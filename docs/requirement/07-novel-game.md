# 07 — ノベルゲーム化（サウンドノベル書き出し・PG 設計）

> 本書は 2026-08 の壁打ちセッションで固めたもの。位置づけは [00-overview.md](./00-overview.md) §1 の「公開は複数ターゲットの一つ」の**4本目**であり、[01-mvp-scope.md](./01-mvp-scope.md) §3「出す」の延長線上にある。
> **新しいアプリは作らない。** exporter を1本増やし、演出データのレイヤを1枚足すだけの話に落とす。

## 0. 位置づけ

小説をそのままブラウザで遊べる**サウンドノベル**に変換する。既存の構図へこう入る:

| 分解した要素 | 置き場所 |
|---|---|
| 小説 → ゲーム化 | leaf の exporter をもう1本（`toNovelGame`） |
| 演出データ（話者・背景・BGM・場面区切り） | leaf の新レイヤ（`Staging`・§2） |
| ブラウザでプレイ | zip 書き出し → 後から grove へ埋め込む |

**設計思想を曲げない**ことが最優先。正本 `Work` は1つのまま、書き出し先が増えるだけ、という形を守る。

### 既に手元にある土台（新規実装が要らないもの）

- `blocksToHtml(blocks, resolvedNames?)`（`src/core/exporter/toHtml.ts`）— 本文 → HTML
- `zipStore(inputs)`（`src/core/zip/index.ts`）— 依存ゼロの ZIP 書き出し。**無圧縮（store）だが、同梱物が WebP / OGG＝既に圧縮済みなので deflate は不要**
- `Block.id`（`src/core/schema/index.ts`）— 演出を本文へ張り付けるアンカー（§2 の要）
- 明朝体フォント一式（Shippori Mincho B1 / Noto Serif JP）— §5 の品質要件で最も効く資産
- R2 バケット `MEDIA` と `userId` プレフィクス運用（`functions/api/sync/work.ts` / `functions/api/backup.ts`）
- MCP サーバ（`functions/api/_lib/mcp-server.ts`）— 演出付けを外部 AI へ委ねる口

## 1. 確定事項

| 項目 | 決定 |
|---|---|
| 形式 | **一本道（分岐なし）**。分岐は入れない（D-GAME-LINEAR） |
| 主軸モード | **立ち絵なし＝サウンドノベル型**（テキスト＋背景＋名前枠）。立ち絵は後段のオプション（D-GAME-NOSPRITE） |
| 単位 | **1話ごと**。作品まるごとではない（D-GAME-EPISODE） |
| 素材 | 運営が用意したテンプレ（背景・BGM）を同梱。背景は**生成AI**で制作（D-GAME-ASSET-SOURCE） |
| 正本との関係 | `Work` は不変。演出は別ドキュメント `Staging` が `blockId` で張り付く（D-GAME-STAGING） |
| 配信 | 第一形態は **zip 書き出し**。grove 埋め込みは後段（D-GAME-DIST） |
| 拡散 | プレイ中の**一行切り出しカード共有**を初期から入れる（D-GAME-SHARECARD） |
| アカウント | **無料枠でもアカウント登録を必須**とする（D-GAME-ACCOUNT） |
| 課金の線 | 作るのは無料／凝るのは有料（§9・D-GAME-PRICE） |
| 対応端末 | **作る作業（演出付け・書き出し）は PC＝広い画面限定。プレイは端末を問わない**（D-GAME-PC） |

## 2. データモデル — 正本を汚さない「演出譜」

### 2.1 なぜ分離するか

`coverImage` / `GlossaryEntry.thumbnail` は「リサイズ済み JPEG の data URL」を `Work` JSON へ直に埋めている。表紙1枚・図鑑サムネならこれで正しいが、**背景×場面数＋BGM を同じ方式で入れると破綻する**（同期は 25 MB/work・1 GB/user＝D-SYNC-CAPACITY、バックアップは 100 MB）。

よって演出は `Work` の外に出す。

### 2.2 スキーマ（ドラフト）

```ts
// src/core/game （純TS・TDD）
type Staging = {
  workId: string
  episodeId: string
  cues: Cue[]                  // blockId をキーに本文へ張り付く（本文は一切書き換えない）
  updatedAt: number
}

type Cue = {
  blockId: string              // ← 既存の Block.id をそのまま使う
  speaker?: string             // 辞書 entry の name（= [[名前]] の解決キーと同一）
  sceneBreak?: boolean         // ここで場面が変わる（背景・BGM の切り替え点）
  bg?: string                  // アセットキー（実体は持たない）
  bgm?: string
  se?: string
  transition?: 'cut' | 'fade' | 'flash'
}

type AssetRef = {
  key: string                  // 'preset:bg/room-night' | 'user:<hash>'
  kind: 'bg' | 'bgm' | 'se' | 'sprite'
  loopStart?: number           // BGM のシームレスループ点（秒）。§4.3
  loopEnd?: number
}
```

### 2.3 blockId アンカーの含意

- **小説を直すとゲームも直る。** 本文を書き換えても `Block.id` が生きていれば演出が残る。
- 逆に「一度エクスポートして向こうで編集する」型は採らない。二重管理になり必ず腐る（D-GAME-STAGING）。
- `blockId` が消えた cue＝**orphan**。`plot` の `foreshadow` にある orphan 判定と同じ考え方で扱い、UI に「行き先を失った演出」として提示する（自動削除しない）。

> **id の安定化（G0 実装時の発見 → 解決済み）**: パーサの id は行番号ベース
> （`parseEpisodeBody` の `b${i+1}`）で、素通しだと保存のたびに振り直されていた。
> 現在は本文を再パースする保存の入口（`editorStore.save`・MCP の `set_episode`）が
> **`reconcileBlockIds`**（`src/core/parser/reconcileBlockIds.ts`）を通し、
> ①内容の完全一致（出現順）→ ②残りの行の位置対応、の2パスで旧 id を引き継ぐ。
> 編集していない行は挿入・削除・移動をまたいで id を保ち、1行の推敲でも id は残る。
> 対応が取れない新しい行だけが新 id になる（出力の id は常に一意）。

### 2.4 永続化（G1 実装済み・実装に合わせて記述を更新）

- `Staging` は `Work` とは**別レコード**として IndexedDB に持つ（`staging:<workId>:<episodeId>`・
  `StagingRepository`）。id は決定的合成＝複数端末が同時に演出を付けても同じレコードに収束する。
- 同期は D-SYNC-MEDIA の doc/media 2分割に**3つ目を足さない**。プロットと同じ
  **種別プレフィックス相乗り**（D-SYNC2-ITEMS・syncId `staging:<workId>:<episodeId>`）で
  同じ D1 works テーブル・API に載る（サーバ無改修）。数 KB なので 25 MB/doc 制限にも遠い。
  旧クライアントは未知の syncId を parse できず読み飛ばす＝ローカル無傷（`plot:` 追加時と同じ前例）。
- **全体バックアップには入る**（`CloudBackupSchema.stagings`・旧バックアップは既定 `[]`）。
  **作品バンドル（kotonoha-leaf-bundle.json）と履歴スナップショットには入らない** —
  プロット・構造レイヤーも同じ現行仕様で、丸ごとの持ち運びは全体バックアップが受け持つ。
  素材の実体はどの経路にも持たない（§4.4）。

## 3. セリフ・地の文・場面の判別

### 3.1 セリフ判定 — ほぼ無料で解ける

正本が「**改行＝1 block**」（[02-notation-and-format.md](./02-notation-and-format.md) §2）なので、判別は block 単位で決まる。

- `「` `『` で始まる block ＝ セリフ。日本語小説の慣習が強く、精度は実用上十分。
- それ以外 ＝ 地の文。
- 空 block（`inlines: []`）＝ 間。ゲーム側では**改ページの候補**として扱う。

### 3.2 話者同定 — ここが本丸。自前推論は持たない

立ち絵・名前枠の生命線だが、ルールベースでは当たらない（体感 60〜70%）。**コトノハは辞書と MCP を持っているので、そこへ寄せる。**

1. **辞書による裏取り** — 地の文の直近 `ref`（`[[名前]]`）を話者候補にする。`resolveRef` で人物が確定するのが強い。
2. **MCP へ委ねる** — `set_staging` ツールを足し、**話者タグ付けと演出付けは外部 Claude にやらせる**。「AI をツールに組み込まない・推論は常にユーザーの AI が行う」（[01-mvp-scope.md](./01-mvp-scope.md) §3.1）と完全に整合する。自前の話者推定エンジンは書かない。
3. **最後は人間** — 演出エディタで1クリック修正できることを前提にし、自動判定の精度に賭けない。

### 3.3 場面区切り — 自動化しない

かつて `＊`（`sceneBreak` ブロック）は廃止され、読み込み時に空段落へ正規化される（`BlockSchema` の preprocess）。**いま正本に明示的な場面区切りは存在しない。**

- 自動**提案**は出す（空 block の連続・話の切れ目・`plot` の beat 境界）。
- **確定はユーザーが行う**。`Cue.sceneBreak` に記録する。
- 正本へ場面区切りを復活させることはしない（EPUB / なろう / カクヨム 書き出しへ波及させない）。

## 4. 素材

### 4.1 運営テンプレ（同梱）

背景は**生成AIで制作**する。実務上の争点は品質ではなく**統一感**なので、そこを設計で担保する。

- **スタイル基準画を1枚作り、それを参照画像として全枚数を生成する**（バラバラに生成しない）
- マトリクスで枚数を抑える: **8場所 × 3時間帯 = 24枚**
  - 場所: 室内 / 廊下 / 街 / 自然 / 夜道 / 空 / 暗転 / 抽象
  - 時間帯: 昼 / 夕 / 夜
- 生成 1920×1080 → 配信 **WebP 1280×720（150 KB 前後）**
- 出力には電子透かし（SynthID 等）が入る前提で設計する＝**AI 生成であることが検出可能な状態を隠す方向の設計にしない**
- 再配布を伴うテンプレ素材という形態になるため、生成サービスの規約の該当箇所を確認する（→ §14 未決）

### 4.2 ライセンスとクレジット

同梱素材をユーザーが zip として配布する＝**再配布**にあたる。

- 運営素材は**再配布可のライセンスで運営が保証する**（ユーザーに規約判断をさせない）
- ゲーム内に**クレジット画面を自動生成**する（使用した素材キーから機械的に組み立てる）
- ユーザーが持ち込んだ素材の権利はユーザー責任（[99-open-questions.md](./99-open-questions.md) のコンテンツポリシーと同じ線＝制限は公開時のみ）

### 4.3 BGM

- **3〜5曲で足りる**: 日常 / 緊張 / 哀愁 / 決意 / 静寂（環境音）。オリジナル制作。
- 実務上の唯一の難所は**シームレスループ**。曲側で完璧なループを作り込まず、**`AssetRef.loopStart` / `loopEnd`（秒）をメタデータで持ち、Web Audio API の `loopStart` / `loopEnd` に流す**。
  - これを後から足すと全曲の作り直しになるため、**最初からスキーマに持たせる**。

### 4.4 保存先

| 種別 | ローカル | 配信 |
|---|---|---|
| 運営テンプレ | アプリに同梱（静的） | **Pages の静的ファイル**（R2 を通さない・帯域無料） |
| ユーザー持ち込み | IndexedDB に Blob | R2（`userId` プレフィクス・既存の purge 運用に相乗り） |

**data URL で `Work` に埋める方式は採らない**（§2.1）。ここが既存の画像方式との明確な分岐点。

> **実装メモ（G2 前半・実装済み）**: 持ち込み背景の**ローカル側**を実装した。
> `src/core/game/assets.ts`（`UserGameAssetSchema`・演出のキーは `user:<id>`）と
> `gameAssetRepository`（IndexedDB・`gameasset:` プレフィクス）。保持形式は Blob ではなく
> **リサイズ済み data URL 文字列**（`gameBgToDataUrl`＝長辺 1280 WebP q0.82。カード共有用の
> tone 3色も同時に抽出）で、実用上十分小さい。`Work` には埋めない（演出 Staging と同じく正本の外）。
> 書き出しは zip に `assets/bg/user-<id>.webp` として**使用分のみ**同梱し、クレジットは持ち込み欄へ振り分け。
> サーバ改修ゼロ・無料。R2 ホスティング（端末間で素材を運ぶ・grove 配信・有料）は G2 後半で別途。

## 5. プレイヤーの品質要件

クオリティを決めるのは絵ではない。効く順に並べ、**上から実装する**。

| 順 | 項目 | 備考 |
|---|---|---|
| 1 | **文字の見た目** | Shippori Mincho B1 / Noto Serif JP を既にバンドル済み。明朝が綺麗に出るだけで印象が決まる |
| 2 | **文字送りの「間」** | 句読点で微小停止、`…` で長め、改行で一拍。数行のコードで別物になる |
| 3 | **オート / スキップ / バックログ / セーブ** | **「ちゃんとしたノベルゲームか」の判定はここでされる。** 無いと簡易ビューアに見える。`localStorage` で足りる |
| 4 | **Ken Burns ＋ クロスフェード** | 背景のゆっくりズーム/パン（CSS transform のみ）。背景も BGM もパツンと切り替えない |
| 5 | **縦書き（オプション）** | EPUB の縦書き資産が流用できる。縦書きサウンドノベルは市場にほぼ無く差別化になるが、スマホ縦持ちが難しいのでオプション扱い |

**到達点の見立て**: 素材力で同人上位作品には勝てない。狙いは「ゲームとしての完成度」ではなく **「小説を読む体験の拡張」**。1〜4 を押さえれば作品として出せる水準に届く。

## 6. 一行切り出しカード共有

拡散の本体はここに置く。**作家が宣伝するより読者が宣伝するほうが強い。**

- プレイ中に任意の一行を選び、**背景＋セリフ＋作品名** を Canvas に描いて PNG 化
- 共有は `navigator.share({ files })`（モバイルは X アプリへ直接渡る）／PC はダウンロード＋クリップボード
- **サーバ不要・クライアント完結**。zip 同梱なら素材はローカル＝ Canvas の CORS 汚染も起きない。grove 配信時は same-origin ないし `crossorigin` 属性で解決する

> **OGP（リンク貼付時に自動表示されるカード）は別物**で、`og:image` を URL で返すサーバ実装が要る。こちらは grove 側の担当として G3 に置く（D-GAME-SHARECARD）。

## 7. 配信ターゲット

| ターゲット | 形 | 段 |
|---|---|---|
| zip 書き出し | `index.html` ＋ `assets/`。itch.io / ふりーむ / 自サイトへそのまま置ける | G0 |
| grove で公開 | 話一覧に「**サウンドノベルで読む**」を並べる。正本が同じなので追加送信は `Staging` のみ | G3 |

grove 側の設計上の要点:

- **読了状態を共有する**（ゲームで読んだら小説側も既読）。別々に持つと読者が混乱する
- いいね・投げ銭は作品単位なので既存のまま効く
- 送信は publish 契約の拡張（v4）が要る。**G0 でプレイヤーを完成させてから交渉する**＝ grove 側は「埋め込むだけ」になり、契約変更が最小で済む

## 8. コスト試算

> ⚠️ 単価は 2026-08 時点の把握であり、**公式の料金ページで再確認すること**（→ §14 未決）。ただし結論は単価が変動しても揺らがない（理由は下記）。

**R2 は egress（転送量）が無料**。ノベルゲーム配信のコストは通常「素材の転送量」が支配的なので、そこが構造的に消えている。

| | 12 MB の作品を月10万プレイ |
|---|---|
| S3 相当（$0.09/GB） | 1.2 TB → 約 $108 / 月 |
| **R2** | **$0** |

さらに運営テンプレは Pages の静的配信（帯域無料）に置くため R2 すら通らない。

**R2 単価（要再確認）**: ストレージ $0.015/GB・月 ／ Class A $4.50 per 100万 ／ Class B $0.36 per 100万 ／ 転送 $0 ／ 無料枠 10 GB・Class A 100万・Class B 1000万。

| シナリオ | 増える容量 | 月額 |
|---|---|---|
| A: 立ち絵なし＋テンプレのみ（主流） | 本文＋`Staging` の数 KB のみ | **測定できないレベル** |
| B: 独自素材あり 100 作品 | 1.2 GB | 無料枠内 |
| B: 独自素材あり 1,000 作品 | 12 GB | 約 $0.18 |
| B: 独自素材あり 10,000 作品 | 120 GB | 約 $1.80 |

**結論: インフラ実費はほぼゼロ。** 本当のコストは開発時間と素材制作時間であり、課金判断は原価回収ではなく値付け戦略の問題になる。

## 9. 課金の線

既存原則「課金の線は**配布ではなく保全**」（`src/ui/_api/publish.ts` のコメント）を壊さない引き方にする。

| 機能 | 線 | 理由 |
|---|---|---|
| zip 書き出し（テンプレ素材） | **無料** | 「持ち出せる」哲学の核。ここを塞ぐと思想が折れる |
| grove で公開・プレイ | **無料** | 実費ゼロ。集客機能なので入口を狭めない |
| **独自素材のホスティング**（R2 容量） | **有料** | 唯一実費が乗る＝「保全」と同じ理屈 |
| **MCP による演出の自動付け** | **有料** | 既存の MCP 有料枠へそのまま乗る |

### アカウント必須の理由づけ

無料枠でも**アカウント登録を必須**にする（D-GAME-ACCOUNT）。コトノハで初めて「アカウント無しでは使えない機能」になるため、理由を明文化しておく:

> **運営素材を同梱した zip を配布する＝素材のライセンス同意が要る。同意の主体を特定する必要があるからアカウントが要る。**

これなら「保全が有料／配布は無料」と矛盾しない。集客の入口が狭まる懸念に対する緩和策（素材なし書き出しのみアカウント不要）は §14 の未決に置き、**まず一律必須で出して登録率を見てから判断する**。

## 10. core 純関数（TDD の主戦場）

```ts
// src/core/game
// 判別:  classifyBlock(block): 'dialogue' | 'narration' | 'gap'   // 「『 で始まるか・空か
// 分割:  toPages(blocks, staging): Page[]                          // 改ページ・場面境界の確定
// 演出:  applyCues(pages, staging): StagedPage[]                   // blockId で cue を突き合わせ
// 健全性: findOrphanCues(staging, episode): Cue[]                  // 消えた blockId を指す cue
// 提案:  suggestSceneBreaks(blocks): string[]                      // blockId 列（提案のみ・確定しない）
// 話者:  suggestSpeaker(blocks, index, entries): string | undefined // 直近 ref からの候補（外れてよい）
// 書出:  toNovelGame(work, episode, staging, assets): ZipInput[]    // zipStore へ渡す形
```

`src/core` は React 非依存を維持する（[03-architecture.md](./03-architecture.md) §2）。Canvas / Web Audio / `navigator.share` は UI 層（`src/ui/_utils`）に隔離する。既存の `imageResizer.ts` と `src/core/image` の分け方に倣う。

## 11. 不変条件（テストで担保）

- `Work` は**ゲーム化によって一切変更されない**（正本の往復恒等が保たれる）
- 本文を編集しても、`Block.id` が生きている cue は保持される
- `Block` が消えたら該当 cue は **orphan として列挙される**（自動削除されない）
- `classifyBlock` が `「` `『` 始まりをセリフ、空 block を gap と判定する
- `Staging` を持たない話でも `toNovelGame` が成立する（＝**演出ゼロでプレイできる**）
- `suggestSceneBreaks` / `suggestSpeaker` は**提案のみ**で `Staging` を書き換えない
- 生成 zip が `index.html` と参照アセットの整合を保つ（参照キーに対応する実体が全て同梱される）
- クレジット画面が、使用した素材キーから機械的に生成される
- `Staging` がバンドル export → 別端末 import で復元される

## 12. 実装順と線引き

| 段 | 内容 | サーバ変更 |
|---|---|---|
| **G0** | `toNovelGame` exporter：セリフ/地の文判別＋改ページ＋テンプレ背景＋名前枠＋§5 の 1〜4＋**一行カード共有**。zip 書き出し | **なし**（カード共有はクライアント完結） |
| **G1** | `Staging` レイヤ＋場面区切り UI＋背景/BGM 選択。話者は辞書から半自動 | なし |
| **G2** | 独自素材の持ち込み（R2 ホスティング・有料）。立ち絵（`GlossaryEntry` の表情スロット拡張） | R2 |
| **G3** | MCP `get_staging` / `set_staging`＋ grove 公開（publish 契約 v4）＋ OGP カード | D1 / grove 契約 |

> **実装メモ（G3 の MCP 部分・実装済み）**: `get_staging` / `set_staging` を実装した
> （ツール定義と配線＝`functions/api/_lib/mcp-server.ts`、純ロジック＝`src/core/mcp-edit` の
> `setStagingCues`、読み出しレンダラ＝`src/core/exporter/stagingToPlainText.ts`）。
> データ源は既存のライブスナップショット（`CloudBackup.stagings`・G1 で相乗り済み）で、
> 反映も既存の「AIの変更を取り込む」経路＝**サーバのストレージ・D1 は無改修**。
> MCP はトークン発行が会員限定なので、D-GAME-PRICE の「MCP 演出は有料」はゲート追加なしで成立。
> `set_staging` は行単位のパッチ（省略＝据え置き・空文字＝削除・`clear` で丸ごと外す）で、
> 一括置換をさせない＝AI の一手ミスで全演出が消えない。grove 公開（契約 v4）・OGP は未着手。

### 線引き

| 区分 | 項目 |
|---|---|
| **G0（最初）** | 「ボタン1つ＋背景を数枚選ぶだけで5分」で遊べる状態まで**完全自動**で出す。演出は任意 |

## 13. 決定事項（確定済み）

| ID | 決定 |
|---|---|
| **D-GAME-LINEAR** | **一本道・分岐なし。** 分岐を入れると正本 `Work` が木構造になり EPUB / なろう / カクヨム 書き出しが壊れる＝「正本は1つ」の破壊。複数ルートが欲しければ別作品として持つ。 |
| **D-GAME-NOSPRITE** | 主軸は**立ち絵なしのサウンドノベル型**。絵を用意できない書き手が大半で、立ち絵前提だと「作れる人が誰もいないツール」になる。立ち絵は G2 のオプション。 |
| **D-GAME-EPISODE** | ゲーム化の単位は**1話**。1話＝3,000〜5,000字＝3〜5分で、SNS から来た読者が完走できるほぼ唯一の長さ。作品まるごとは対象外。 |
| **D-GAME-STAGING** | 演出は正本の外に `Staging` として持ち、**`Block.id` でアンカーする**。`Work` へ素材を埋めない（25 MB/work 制限・D-SYNC-CAPACITY）。「エクスポート先で編集」型は二重管理になるため採らない。orphan cue は自動削除せず列挙する。 |
| **D-GAME-SCENE-MANUAL** | 場面区切りは**自動提案・手動確定**。正本に `sceneBreak` を復活させない（他ターゲットへ波及させない）。 |
| **D-GAME-SPEAKER-MCP** | 話者同定の自前推論エンジンは**持たない**。辞書 `ref` による候補提示＋ MCP 経由の外部 AI（`set_staging`）＋人手修正で成立させる。「推論は常にユーザーの AI が行う」と整合。 |
| **D-GAME-ASSET-SOURCE** | 運営テンプレの背景は**生成AI**で制作。統一感はスタイル基準画の参照＋8場所×3時間帯のマトリクスで担保。電子透かしが入る前提で設計し、隠す方向へは倒さない。BGM はオリジナル3〜5曲。 |
| **D-GAME-ASSET-STORE** | 運営テンプレは **Pages の静的配信**（R2 を通さない）。ユーザー持ち込みのみ R2（`userId` プレフィクス・既存 purge に相乗り）。data URL 埋め込みは不採用。 |
| **D-GAME-BGM-LOOP** | BGM のループ点は**素材のメタデータ**（`loopStart` / `loopEnd` 秒）として持ち、Web Audio API へ流す。後付けすると全曲作り直しになるため初期からスキーマに入れる。 |
| **D-GAME-SHARECARD** | **一行切り出しカードは G0 に入れる**（Canvas ＋ `navigator.share`・**サーバ不要**）。拡散の本体は「読者が広める」導線。`og:image` を返す OGP は別物で grove 側・G3。 |
| **D-GAME-DIST** | 第一形態は **zip 書き出し**（`zipStore` の無圧縮で足りる＝同梱物が既に圧縮済み）。grove 埋め込みは G3。**プレイヤーを先に完成させてから grove 契約 v4 を交渉する**＝先方の実装が「埋め込むだけ」になる。 |
| **D-GAME-ACCOUNT** | 無料枠でも**アカウント登録を必須**。根拠＝運営素材を同梱した zip の配布にはライセンス同意が要り、同意主体の特定が必要。コトノハで初のアカウント必須機能になるため、この根拠を明文で維持する。 |
| **D-GAME-PRICE** | 作るのは無料（zip 書き出し・grove 公開）／凝るのは有料（独自素材の R2 ホスティング・MCP 演出）。インフラ実費はほぼゼロ（§8）なので、有料化は原価回収ではなく値付け戦略として扱う。既存の「配布は無料・保全が有料」と矛盾させない。 |
| **D-GAME-QUALITY** | 品質の優先順は 文字組 ＞ 文字送りの間 ＞ オート/スキップ/バックログ/セーブ ＞ Ken Burns/クロスフェード ＞ 縦書き。**絵の量ではなく上位3つが「ちゃんとしたノベルゲーム」の判定を決める。** |
| **D-GAME-PC** | **作る作業は PC（広い画面・1024px 以上）に限定**する（2026-08 決定）。演出エディタは構想の道具と同じ入口ゲート（`App.tsx` の `stagingAvailable`）、書き出しも ExportDialog の game 形式を同じ幅（`useIsNarrow`）で制限。**プレイは端末を問わない**——書き出した zip のプレイヤーはスマホ対応を維持し、grove 公開分（G3）もスマホで遊べる想定。MCP の演出付けはサーバ側で端末非依存のまま。 |
