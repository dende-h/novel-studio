# 投稿サイト向けの原稿取込とTXT書き出しの仕様案

2026年11月27日更新。コトノハ-leaf-を執筆・推敲のエディタとして使い、作者が既に使っている投稿先へ原稿を持ち込めるようにする。

## 一括リリースの範囲

対応サイトの原稿取込・投稿用TXT書き出し、ホームの作品／複数話取込、各話の編集画面の本文取込、登録不要の公開記法変換ページ、カクヨム互換の作品ZIP出力を**同じリリースで公開する**。投稿サービスごとの取込形式は下の表で定義する。作者用のファイル出力を確認できないサイトも、投稿先の記法を解析するTXT・貼り付けに対応する。作者用バックアップの原本が存在するサイトは、そのZIP・TXT・PDF等をLeafに直接選べるようにし、公開前に実データで照合する。

原稿取込で必須なのは、**各話のタイトルと本文、複数話のときは話順**。作品名が出力に含まれていれば拾い、含まれなければ仮の名前を出して編集できるようにする。前後書き、章階層、タグ、予約日時、挿絵の実体などは、形式から読み取れるものを補足として扱う。

## ホームから作品・複数話を取り込む

- ホームの作品一覧に「原稿を取り込む」を置く。「ファイルを選ぶ」「フォルダを選ぶ」、ドラッグ＆ドロップ、貼り付けから入る。複数TXT、フォルダ、ZIP、対応PDF・EPUBを同じプレビューで扱い、入力を後から追加できる。フォルダやZIPの相対パスを保持して話順や同名ファイルの判定に使う。フォルダ選択が使えない環境では、複数ファイルまたはZIPを選べる。入力はブラウザ内で処理する。
- 保存先は「新しい作品を作る」「既存作品に話を追加」。新規作成では作品名と各話のタイトルを読み取る。原稿に作品名がない場合はZIP名・フォルダ名、または先頭のファイル名を仮の作品名にする。話名がなければ拡張子を除いたファイル名、貼り付けの場合は「第1話」などを使う。タイトルはプレビューで変更でき、同じタイトルの既存作品も表示する。既存作品への追加は作品を選び、確認した話を既存の最後に追加する。既存の話を置き換える操作は各話の編集画面で行う。
- ファイルの種類と中身を確かめ、公式バックアップの構造が判明したときは連番や目次どおりに話を作る。汎用TXT・フォルダ・ZIPでは相対パスの自然順で「1ファイル＝1話」を初期値とする。1本の本文を「見出し行で分ける」、複数ファイルを「1話にまとめる」こともプレビューで選べる。別々の作品のバックアップが混ざっている場合は出所ごとに表示し、どの話を取り込むかを確認する。
- 確定前に作品名、話順、話タイトル、本文を確認する。章・公開済み・下書きなどの出所を読み取れた場合は補足として表示し、取り込みたい話を選べる。話名、並び順、分割・連結を編集でき、元の長い題名と末尾改行も保持する。
- Leaf内の保存は非公開の新規作品または新規話として行う。元サイトの公開予約を引き継がない。`Work` の作品名と `Episode` の話名・本文を保存する。著者・紹介文は読み取れたときに既存の欄へ入れる。章ラベル、前後書き、タグ、公開状態などは読み取れた分を「取込情報.txt」にまとめ、前後書きは任意で本文にも含められる。話の範囲は分かっていて前後書きだけ分離できない場合は、文章を省かず本文に含め、プレビューで知らせる。感想・レビュー・反応数が別ファイルにあると分かる場合は、本文の候補から外す。

## 話の編集画面から本文を取り込む

- 開いている話のメニューに「本文を取り込む」を置く。TXT1ファイルか貼り付けを受け付け、サイトや記法の選択なしで本文上の記法を自動解析する。公式の話TXTと判定できた場合はヘッダーと本文を分け、元の話名・前後書き等をプレビューで確認できる。作品ZIP、複数ファイル、複数話と判定された入力はホームの「原稿を取り込む」へ案内する。
- 本文が空なら「本文に入れる」。本文がある場合は「末尾に追加」「本文を置き換える」から選ぶ。確定前に変更後の本文と警告を表示する。開いている話のID・タイトルは維持し、変更は既存の下書き保存の経路に載せる。保存前に話を切り替えたり別の編集が入った場合は、変更を適用せず最新の本文で再確認する。置換は取り消しでき、エラー時は元の本文を保持する。

## ファイル形式と保存前の検証

- 本文を解析する前に、ファイルの拡張子と実際の内容、文字コード、ZIPの構造と上限を確認する。画像を `.txt` に改名したもの、復号できないTXT、壊れたZIP、対応する原稿が入っていないZIPはエラーにする。
- 公式バックアップと判定した入力は、本文を抽出し、話ごとの範囲と順序を確認できる構造か検査する。話名が欠けていても仮の名前で確認できる場合や、付帯情報だけが欠けている場合は取込を続ける。対象の話や本文を取り出すために必要な構造が欠けている場合は、その入力をエラーにする。
- エラーにはファイル名と理由を表示する。話の編集画面では現在の本文を維持する。ホームで複数の入力がある場合は、成功した入力のプレビューを残す。エラーのある入力を差し替えるか、利用者が一覧から外すまでは確定できない。確定前に取り込み結果のスキーマとサイズを再検査し、失敗した作品や話は保存しない。

## 取込時の記法の自動判定

- 本文の解析は、サイトを一つに絞ってから行う必要はない。`｜漢字《かんじ》` や `[[rb:漢字 > かんじ]]` のようにルビと判定できる記法は共通のルビに変換する。通常の括弧書きと区別しづらい `漢字（かんじ）` などは、出所が分からない状態では文字のまま保持する。公式ファイルとして入力元を特定できた場合は、そのサイトの記法を適用する。
- 判定が難しい場合はプレビューで原文と変換後を比べられる。必要なときだけ「元の記法を指定」「記法を変換しない」を選べる。未知のタグ、閉じ記号がない記法、曖昧な部分は元の文字列のまま本文に入れる。ほかの箇所の解析は続け、未解析の記法だけで取り込みを止めない。表示してから編集・再保存しても、その文字列を維持する。普通のTXTも同じ入口で取り込める。

## Leafからの書き出し

- ホームの左サイドバー、作品のメニュー、話の編集画面の上部から「書き出し」専用ページを開く。左に書き出し形式を表示し、執筆から開いた場合は元の作品・話へ戻す。Web投稿形式は投稿先・対象話を選び、「本文をコピー」または1話ずつTXT／Word（.docx）で保存する。確認モーダルにはコピー・保存される記法付きの本文を表示し、Wordにも同じ本文を入れる。投稿先の取り込みを実機確認できた場合に限り、その投稿先向けの複数話ZIPを案内する。
- 既定はUTF-8／LF。投稿先が指定する場合は文字コード・BOM・改行を選べるようにする。変換後の文字数とTXTの大きさを表示する。TXTの文字コード・改行・BOM、およびファイルの大きさは、ⓘの説明モーダルで確認できる。親文字の範囲が変わる場合は明示縦線を出す。文中の括弧等は投稿先の書式でエスケープする。元のLeaf原稿は保存内容を変えず、変換できない読みに対しては該当箇所を表示し、修正か未変換出力を選べるようにする。
- Leaf固有の用語参照は表示名に展開する。元の記法をそのまま使える装飾は投稿先に合わせて出力し、対応できない章・改ページ、太字・斜体・リンク、挿絵やその他のタグは位置を伝える。知らないタグを削らず、出力する地の文とプレビューを確認できるようにする。

## カクヨム互換の作品ZIP

- カクヨム互換ZIPは原稿取り込みに対応する。作品情報ファイルと話別TXTを読み、作品名・話タイトル・話順・本文を復元する。
- ホームの原稿取込では、カクヨムの公式ZIPに加え、NoveLand・MonokakiMeisterが作ったカクヨム互換ZIPを同じ形式として受け付ける。判定は内部の目次と話ファイルの構造で行う。既知の付記や作品情報の差は許容し、本文・話名・話順を確認する。 [NoveLandの一括出力](https://noveland.discourse.group/t/topic/386) · [MonokakiMeisterの一括出力](https://note.com/lumidina/n/nbc5f3a490e0b)
- カクヨムでの投稿には1話ごとの投稿用TXT・コピーを使う。カクヨム公式の作品ZIPは作者向けバックアップであり、カクヨムへの一括投稿には使えない。 [カクヨム公式](https://kakuyomu.jp/help/entry/download_works)

## 登録不要の記法変換ページ

本番の公開URL `/notation-converter/` に「小説のルビ・傍点 記法変換」を作る。Leaf紹介サイトからもリンクする。投稿先を選んで原稿を貼り付けるかTXTを開くと、Leafが元の記法を自動判定し、変換後の本文・警告・挿絵位置を表示する。コピーとTXT保存はログイン不要。変換はブラウザ内で行い、原稿をサーバー・アクセスログ・URLに送らない。「この原稿で書き始める」を押したときだけ、同じ端末のLeafの新規作品プレビューへ引き継ぐ。投稿先に合わせた変換エンジンは編集画面と共通にする。

## 実装前の差分と設計上の要点

- 実装前のなろう・カクヨム出力は選択話1件のTXTだった。漢字が連続して親文字の範囲が広がる、なろうのかな以外の読みで縦線が省略される、カクヨムで地の文の `《` がエスケープされない、両者ともルビの上限を検査しない、という差分がある。既存の関連テストは10ファイル184件通過。 [なろう出力](../../src/core/exporter/toNarou.ts) · [カクヨム出力](../../src/core/exporter/toKakuyomu.ts)
- 実装前のホームのTXT取込はUTF-8／Shift_JIS、既存の見出し・ファイル分割まで対応していた。汎用パーサは `[[...]]` をLeaf参照にするため、外部記法の入力とLeaf正本を読み分ける。外部の記号を編集・再保存しても意味が変わらないよう、既存のフォルダ／一時下書きの読み戻しを含めた正本記法の往復を検証する。 [既存取込仕様](COT-31/spec.md) · [本文パーサ](../../src/core/parser/parseNotation.ts)
- ファイル選択、フォルダ選択、ZIP展開の結果を「相対パス・元の入力・内容」の共通形式に揃える。専用の構造判定、文字コード復号、話の分割、本文の記法解析は入力方法に関係なく共用する。ZIP読み取り・復号・各話への分割はブラウザのWorkerで行う。展開前後のサイズ、ファイル数、重複パス、破損・暗号化・入れ子を検査し、読み込めない原因を表示する。既存の入力・作品JSON上限20MiBを維持し、長編は利用者が取り込む話を分けられるようにする。HTML・EPUBのスクリプトや外部画像を実行・取得せず、選択したファイルの内容から変換する。
- PDFは文字層としおりを使い、本文の順序と話の区切りを保存前にプレビューと元ページで確認する。縦書き、段組、ルビなどで文字が欠けるか順序が崩れる場合は、TXTを選ぶか、元の編集画面から本文をコピーして貼り付けるよう案内する。文字層がないPDFにも同じ案内を表示する。

## 一括公開前に照合するファイル

- **一括公開の必須確認は、話タイトル・本文・複数話の順序。** なろうは公開された実例で2種類の開始区切りと見出しが分かった。公開話と下書きの実ファイルで、最終話の本文終端、短編の構造、下書き側にも同じ区切りがあるかを検証する。ノベルアップ＋・アルファポリス・TALESは、複数話を含む作者用出力で話タイトルと本文の位置を照合する。エブリスタは作者PDFで本文の読順と、各話を確認できる取り込み結果を検証する。NOVEL DAYSは提供開始後に一般小説・チャットノベルそれぞれで題名と本文を抽出できるか確認する。これらの作者用原本は手元のプロジェクトに見つかっていない。
- カクヨムは作者の短編・連載の現行ZIPと、NoveLand・MonokakiMeisterの出力で照合する。ソリスピアは同サイトの作品テキストのタイトル・本文・話順を確かめる。アカツキは公開TXT ZIP5作品とHTML ZIP1作品で構造を確認済み。ハーメルンのPDF／EPUBでは本文とその順序を照合する。
- 本文の確認には空行・記号・未解析の記法が欠落しないことを含める。付帯情報や挿絵は、対応できる範囲を実ファイルで確認する。実物で確認できない付帯情報の復元は一括公開の条件に含めない。投稿用TXTの案内は、取込・書き出し画面の操作に合わせ、「原稿の取り込み方」「各サイトへの投稿用TXTの使い方」として表示する。
- 受け入れテストでは、同じ原稿を複数TXT・フォルダ・ZIPで読み込み、話順と本文が一致することを確認する。ホームから作品作成・既存作品への複数話追加、話の編集画面でサイト未選択のまま本文を取り込む操作、括弧表現を誤変換から戻せること、未知のタグや未閉鎖の記号を含む本文が原文のまま保存されること、登録せず変換して保存する操作を確認する。画像を改名したTXT、復号エラー、破損ZIP、既知の形式で必須構造が欠けたファイル、成功・失敗の入力が混ざった場合には、対象が確定されるまで原稿が変わらないことも確認する。カクヨム形式・互換ZIPはLeafの取り込みで作品名・話タイトル・順序・本文を確認する。各投稿先のプレビュー、既存のLeafバックアップ・EPUB・コトノハ-grove-連携も確認する。

## 公開資料から作った検証用ファイル

外部サービスを利用している人の実ファイル提供を必要とせず、公開の公式資料と作者・開発者の取得例からテスト入力を作る。 内容は連作「青い灯りの観測日誌」全3話。各話は、改行およびルビ・傍点の記法を除いて949字、1,001字、991字。一括取込用ファイルには全3話、1話用TXTには約1,000字の第1話を収録する。

- 公開資料で構造を確認できたカクヨム・カクヨム互換、なろうの2書式、アカツキは、その構造を使って架空の原稿を用意した。ノベルアップ＋、TALES、アルファポリス、ソリスピアは、分かっている外側の形だけを採用し、未公開の区切りは仮書式として明示した。エブリスタ想定の縦書きPDF、ハーメルン想定の標準EPUB、NOVEL DAYSなどの本文TXT、拒否テスト用の入力も用意した。

- 検証用読み取りコードで27件が通過。Leafの既存TXT取込にも架空ファイルを使った3件を追加し、関連テスト144件が通過した。公式出力の未確認箇所と、新規ZIP・PDF・EPUB取込の本体実装は、合成試験とは別に追跡する。

- ファイル構成・各書式の出典・再生成方法はリポジトリの `docs/specs/posting-import-fixtures/README.md`。同フォルダの `expectations.json` で基準の原稿、`results.txt` で検証結果を確認できる。

## レビュー後の記法の確認範囲

エブリスタ・カクヨムでは地の文の《の前に縦線を置きます。なろうとノベルアップ＋では、ルビと誤解釈される括弧にも縦線を置きます。ハーメルンでは、地の文が傍点と同じ形のときは、公式説明の無効化記法を使います。Leafでは各サイトの記法を指定した再取り込みまで合成原稿で照合しました。 [エブリスタ](https://support.estar.jp/hc/ja/articles/360020301874) · [カクヨム](https://kakuyomu.jp/help/entry/notation) · [なろう](https://syosetu.com/helpcenter/helppage/helppageid/42) · [ノベルアップ＋](https://novelup.plus/help/detail/ルビを振る) · [ハーメルン](https://syosetu.org/?fid=25&mode=readme_view)

なろうで自動ルビに見える《と、TALESでルビ・傍点に見える《や半角丸括弧には、Leafが縦線を加えます。投稿先の実表示は未確認なので警告を表示します。取り込み時に元の投稿先を指定すると、加えた縦線を外して地の文に戻します。アカツキとソリスピアでは、無効化方法が未確認の記号を維持して確認を促します。アカツキの公式資料は括弧の前に空白を入れる方法を案内しています。 [なろう](https://syosetu.com/helpcenter/helppage/helppageid/42) · [TALES](https://note.com/tales_story_/n/n44f45415e370) · [アカツキ](https://www.akatsuki-novels.com/supports/manual/post)
