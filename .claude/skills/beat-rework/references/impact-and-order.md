# 波及範囲の洗い出しと、書き込みの順番

ビート 1 枚には、伏線・秘密・プロットライン・用語集・本文・幕の並びが、id と位置を通じてぶら下がっている。
**1 枚動かすと、警告を出さずに壊れるものがある。**
ここに書くのは、何が壊れるか、壊さない順番、書いたあとの検算。`get_plot` の出力の見方まで落として書く。

直し方の 3 案の作り方と、作者へ出す文面は `structure-angles.md` §10。
器の分かれ方と書き込みの共通規約は `kotonaha-editing-common/references/kotonaha-mcp.md`。

---

## 1. 着手前に、いまの状態を控える

検算（§7）は「増えていないか」で行う。**基準が無いと増えたことに気づけない。**

`get_plot` の「伏線:」と「秘密（読者に伏せる情報）:」のブロックを、そのまま控える。
状態の印は各行の先頭に出ているので、行ごと持っておけば後から数え直せる。
件数を数えるのは、20 件を超えて行が長すぎるときだけでいい。
控えた数字が間違っていると、検算そのものが嘘になる。

あわせて、幕とビートの数、`対応話` が付いているビートの数、
`（削除済みビート）` の出現回数を同じ場所に書き出しておく。

```
改修前（2026-08-28 時点）
伏線:
- [回収済] 母の指輪 [foreshadow_id: fs-3]（張る: 台所の朝 → 回収: 島を出る）
- [未回収] 錆びた鍵 [foreshadow_id: fs-1]（張る: 港で待つ → 回収: 未定）
  …（残りも行のまま控える）
秘密（読者に伏せる情報）:
- [開示未定] ユキの正体 [secret_id: sc-1]（読者に明かす: 未定 ／ 真相: 母の妹の子）
幕 4 ／ ビート 23 ／ 対応話つき 9 ／「（削除済みビート）」0 件
```

`（削除済みビート）` は、伏線・秘密が指しているビートが既に消えているときに出る文字列。
改修前から 1 件でもあるなら、それは今回の改修より前からある壊れなので、
混ぜずに別件として作者へ報告する。

`※ 他に N 件のプロット案があります` の行が出ていたら、`get_plot` の先頭に出ているプロット名を
読み上げて「これで合っていますか」と 1 行で確かめる。
主プロットは作者が選んだものではなく、中身の多いほう（幕・ビート・ライン・伏線・秘密・世界観設定の
合計数、同数なら更新の新しいほう）が自動で選ばれる。
作者が「いま使っているのはこっち」と思っている案と食い違うことがある。
MCP から対象を切り替える手段は無いので、違うならアプリ側での作業になる。

## 2. 対象ビートを特定する — 伏線・秘密の行に beat_id は出ない

ビートの行には id が出る。

```
3. [確定] 港で待つ [beat_id: b-7a2]
   要約: ユキは桟橋で三時間、船を見送る
   視点: ユキ ／ 登場: ユキ、母 ／ 舞台: 桟橋 ／ 作中時間: 三日後の夕方
   ライン: ユキの決断 ／ 予定: 3,000字 ／ 対応話: 第七話 [episode_id: ep-07]
```

ところが伏線と秘密の行は、参照先を **id ではなくビートのタイトルへ解決して**表示する。

```
伏線:
- [未回収] 錆びた鍵 [foreshadow_id: fs-1]（張る: 港で待つ → 回収: 未定）
秘密（読者に伏せる情報）:
- [開示未定] ユキの正体 [secret_id: sc-1]（読者に明かす: 未定 ／ 真相: 母の妹の子）
```

`b-7a2` で全文検索しても、この伏線は引っかからない。
辿るには、対象ビートのタイトル文字列（ここでは「港で待つ」）で `get_plot` 全文を検索する。

同じタイトルのビートが 2 枚あると、この方法では区別がつかない。
その場合は改題を**作者に提案する**。追跡の都合で、作者が付けた題を勝手に変えない。
紐付けは壊れないが、伏線・秘密の行は参照先をタイトルで表示するので、作者の画面の見え方は変わる。
改題しないと決めたなら、位置（何幕の何番目）で特定して進める。

## 3. 触るビートごとに、つながりを拾う

対象ビート 1 枚につき、次を全部埋める。埋まらない欄があるまま書き込みへ進まない。

### 3.1 伏線（`plant_beat_id` / `payoff_beat_id`）

タイトル検索で、そのビートが `張る:` か `回収:` に出ている伏線を全部拾い、`foreshadow_id` を控える。

| そのビートをどうすると | 伏線はどうなる |
|---|---|
| 削除する（張る側だった） | 回収側が残っていれば `[根なし]`、両方消えれば `[未配置]` |
| 削除する（回収側だった） | `[未回収]` に戻る |
| 別の幕へ動かす | 状態は変わらないが、**張る→回収の順序が逆転していないか**は検査されない |

順序逆転は導出ロジックが見ていない。物語順（幕の並び → 幕内の並び）で、
張るビートが回収ビートより後ろに来ていないかは自分で目視する。

### 3.2 秘密（`reveal_beat_id`）

同じくタイトル検索で `読者に明かす:` に出ている秘密を拾う。

参照先のビートを削除すると `[開示未定]` に落ちる。ここに追加の罠がある。
**`reveal_beat_id` を設定した時点で、その秘密の「明かさない」印は消える**
（明かすビートが決まっている秘密に「最後まで伏せる」印を残さない設計）。
だから「明かさない」だった秘密に一度 `reveal_beat_id` を付け、あとでそのビートを消すと、
`[明かさない]` には戻らず `[開示未定]` になる。

元へ戻すには、`reveal_beat_id: ""` と `keep_hidden: true` を**同じ呼び出しで一緒に**渡す。
`keep_hidden` は、その秘密に明かすビートが残っているあいだ捨てられる。
削除済みのビートを指したままの id も「残っている」に数えるので、
`keep_hidden: true` だけを渡しても表示は `[開示未定]` のまま動かない。

### 3.3 プロットライン（`line_ids`）

ビート行の `ライン: ユキの決断` は名前だけで、`line_id` は出ない。
id は `get_plot` の冒頭にまとまっている。

```
プロットライン: 本筋 [line_id: ln-1]、ユキの決断 [line_id: ln-2]、母の側 [line_id: ln-3]
```

配列を組み直すときは、ここで名前から `line_id` を引く。
ラインを丸ごと消すと（`delete_plot_item` の `kind: line`）、全ビートの `line_ids` から自動で外れる。
**参照を自動で掃除する削除はこれだけ**なので、ラインの削除は影響が広い。

### 3.4 視点・登場・舞台（用語集の `entry_id`）

ここも `get_plot` には名前しか出ない。`entry_id` は `get_glossary` の `[entry_id: …]` で引く。

見えない壊れ方が 2 つある。

- **存在しない `entry_id` を渡してもエラーにならない。** `line_ids` だけは実在チェックがあるが、
  `pov` / `cast` / `place` / `episode_id` は素通りする。id を打ち間違えると、
  書き込みは成功したのに `get_plot` の `登場:` からその名前が消える。消えたようにしか見えない
- **用語集の項目を削除すると、参照していたビートの欄から名前が減る。** 警告は出ない。
  改修前後で `登場:` の顔ぶれが同じかを見る

### 3.5 対応話（`episode_id`）と `status`

`対応話: 第七話 [episode_id: ep-07]` が出ていたら、そのビートには本文がある（§4）。

`status` は `検討中` / `確定` / `執筆中` / `済` の 4 つ。
`執筆中` と `済` は、`episode_id` が付いていなくても「もう書いた」の申告として扱う。

### 3.6 作中時間（`time_label`）

`三日後の夕方` のような相対表現は、直前のビートを基準にしていることが多い。
ビートを並べ替えると、文字列はそのままで意味だけがずれる。
並べ替えの対象になった区間の `作中時間` は、順に読み直して辻褄を確かめる。

### 3.7 幕内の位置（`index`）と予定文字数

`get_plot` はビートを **1 始まり**で番号付けして表示するが、`upsert_plot_beat` の `index` は
0 始まり。表示上「3.」のビートの `index` は `2`。

幕の見出しには小計が出る。

```
## 第二幕・前 [section_id: s-2]（5ビート・予定 14,000字）
```

`target_length` が 1 件も入っていない作品では、この小計は `（5ビート）` としか出ない。
ビートを幕をまたいで動かすと小計が両方の幕で変わるので、
連載のペース配分を作者が数字で持っているなら、動かす前後の小計を並べて見せる。

## 4. 本文が書かれているビートは、本文の改稿とセットでしか動かせない

洗い出しに入る前に、1 行だけ聞く。

> いま何話まで書けていますか。そのうち、公開済みはどこまでですか。

`対応話` と `status` は、本文があることの十分な合図だが、必要な合図ではない。
**紐付けていない話は普通にある。** 作者はプロットを後から作ることも、話を先に書いてしまうこともある。
`対応話` が付いていないビートを「本文なし」と決めて動かすと、書いた原稿の順番を勝手に変えたことになる。

答えが「第八話まで、公開は第五話まで」なら、線は 3 本になる。
公開済み（読者がもう読んだので、並べ替えは実質できない）、書いたが未公開（改稿とセットで動かせる）、
未執筆（自由）。この線を引いてから §4.1 の表を使う。

### 4.1 線引き

| ビートの状態 | 動かしてよいか |
|---|---|
| `検討中` / `確定` で `対応話` なし | 自由。要約・順番・削除まで作者の合意だけで足りる |
| `執筆中` / `済`、または `対応話` あり | **本文の改稿とセット。** 単独では動かさない |

`対応話` の有無が最も硬い信号。`status` は付け替え忘れが起きるが、`episode_id` は
作者が明示的に紐付けたものなので、付いているなら本文が存在する。

### 4.2 何をすると本文が壊れるか

- **要約・メモの書き換え**（`summary` / `note`）… 本文と食い違うだけで、本文は壊れない。
  ただし食い違ったままにすると、次に本文を書く人（作者でも AI でも）が要約を信じて誤る。
  ずれるなら、そのずれを `note` に 1 行残す
- **`index` / `section_id` の変更**（並べ替え・幕移動）… 読者が読む順が変わる。
  該当話とその前後の話で、既出・未出の情報が入れ替わる。改稿必須
- **`pov` の変更** … 本文の人称・視点そのものの変更。全面改稿
- **削除** … `delete_plot_beat` で消えるのはビートのカードだけで、本文の話は消えない。
  話は残り、どのビートからも参照されない「孤児の話」になる。データは失われないが、
  プロットと本文の対応が切れるので、話をどうするか（残す・統合する・作者が消す）を必ず決める

### 4.3 作者への確認の骨格

**黙って動かさない。** 確認は次の骨格で出す。

1. 対象を列挙する（ビートの題・`status`・`対応話`・執筆済みの字数まで）
2. 動かすと本文のどこが通らなくなるかを 1 文で言う
3. 選択肢を 3 つ（`structure-angles.md` §10）
4. 推しとその理由
5. 決まるまで書き込まないと明言する

文面の実例は `structure-angles.md` §10.2。

## 5. 書き込む — 順番を守る

### 5.1 順番

```
0. create_backup（まとまった書き換えの前。cloud 会員のみ。失敗したら作者へ伝えて可否を聞く）
1. 幕が足りなければ upsert_plot_section で先に作る（beat の section_id に要るため）
2. 新しいビートを upsert_plot_beat（id を渡さない）で作り、返ってきた beat_id を控える
3. 位置を決める（section_id と index）
4. 伏線 upsert_foreshadow の plant_beat_id / payoff_beat_id を新しい beat_id へ張り替える
5. 秘密 upsert_secret の reveal_beat_id を張り替える
6. 最後に、不要になったビートを delete_plot_beat で消す
```

### 5.2 なぜこの順番なのか

`upsert_foreshadow` の `plant_beat_id` / `payoff_beat_id` と `upsert_secret` の `reveal_beat_id` には
実在チェックがある。存在しないビート id を渡すと `… のビートが見つかりません` で弾かれる。
だから張り替え先のビートが先に無いといけない。

逆に、古いビートを先に消すと 2 つのことが起きる。伏線が `[根なし]`、秘密が `[開示未定]` に落ち、
その状態がライブスナップショットに保存される。この間に作者がアプリを開くと、壊れた途中経過を見る。
**壊れた状態を一度も保存しない順番が、この順番。**

### 5.3 幕を削除するときの挙動

`delete_plot_item` の `kind: section` は、幕の中のビートを隣の幕の末尾へ移す。
隣は前の幕が優先で、先頭の幕を消したときだけ次の幕になる。ビートは消えない。

ただし移った先では末尾に付く。元の並び順は保たれるが、位置は幕の最後になる。
幕を消したら、移動したビート群の `index` を必ず組み直す。

**最後の 1 幕は削除できない**（`最後の幕は削除できません（ビートの行き場が無くなるため）`）。
幕を減らして 1 つにしたいなら、先に全ビートを残す幕へ移してから、空になった幕を消す。

幕の並べ替えは `upsert_plot_section` に `id` と `index` を渡す。

### 5.4 書き込みはアプリへ即時には映らない

MCP の書き込みが入るのはライブスナップショット側で、
作者のアプリには「AIの変更を取り込む」を押すまで反映されない。

だから、書き込む前に「いまアプリでプロットを編集していないか」を聞く。
両側で同じプロットを触ると、取り込みのときにどちらかが負ける。
書き終えたら、取り込みが要ることを 1 行添える。

## 6. パッチ方式の落とし穴

`upsert_plot_beat` は渡した項目だけ書き換える。省略は据え置き、空文字は未設定へ戻す。
据え置きたいものを渡さないのが最も安全（`kotonaha-mcp.md` §5.1）。
`upsert_glossary_entry` と違うのは配列の扱い。

### 6.1 配列は丸ごと置換される

`cast` / `place` / `line_ids` は、渡すとその内容で置き換わる。追記ではない。

```jsonc
// 悪い例：登場人物に「船頭」を 1 人足すつもり
{ "work_id": "w1", "id": "b-7a2", "cast": ["gl-boatman"] }
// → 結果：登場が「船頭」だけになる。ユキと母が消える
```

```jsonc
// 正しい：現在の全員を entry_id で並べ、そこへ 1 人足した配列を渡す
{ "work_id": "w1", "id": "b-7a2", "cast": ["gl-yuki", "gl-mother", "gl-boatman"] }
```

現在の全員は `get_plot` の `登場: ユキ、母` から名前で読み、`get_glossary` で `entry_id` に引き直す。
`get_plot` には `entry_id` が出ないので、この往復は省けない。

### 6.2 `place` は配列だが、画面には 1 つしか出ない

`upsert_plot_beat` の `place` は配列を受けるのに、アプリのビート編集画面の「舞台（場所）」は
**先頭の 1 件しか表示しない**（`src/ui/components/PlotView/plot-view.tsx`）。
MCP から 2 件書くと、作者の画面には 1 件目だけが見える。しかも作者がその欄に触ると、
選び直した 1 件だけの配列に畳まれ、2 件目が消える。

だから舞台は 1 ビート 1 件で書く。2 か所にまたがる出来事なら、それはビートを 2 枚に割る合図でもある。
どうしても 2 件要るなら、作者に「画面には 1 件しか出ない」ことを伝えてから書く。

このとき、用語集から消えた項目を指す参照は `get_plot` に名前が出ていないので、
組み直した配列からは落ちる。掃除にはなるが、気づかないうちに何かを落としている可能性があるので、
改修前後で登場人数が合っているかを見る。

### 6.3 空文字と 0 の効き方

| 渡すもの | 起きること |
|---|---|
| `summary: ""` | 要約が消える。ガイド文の表示に戻る |
| `note: ""` | メモが消える |
| `pov: ""` | 視点が未設定に戻る |
| `time_label: ""` | 作中時間が未設定に戻る |
| `episode_id: ""` | 本文との紐付けだけが切れる（話そのものは消えない） |
| `target_length: 0` | 予定文字数が未設定に戻る。幕の小計からも抜ける |
| `title: ""` | 何も起きない。空のタイトルは無視され、元のタイトルが残る |
| `cast: []` | 登場が空になる（`[]` は「空の配列で置換」であって、省略とは違う） |

伏線・秘密の参照も同じで、`plant_beat_id: ""` / `payoff_beat_id: ""` / `reveal_beat_id: ""` を渡すと
参照が外れ、表示が `未定` に戻る。張り替え先が決まっていないときの逃げ道になる。

### 6.4 `section_id` と `index` の組み合わせ

| 渡し方 | 起きること |
|---|---|
| `index` だけ | いまの幕の中でその位置へ並べ替え |
| `section_id` と `index` | その幕のその位置へ移動 |
| `section_id` だけ | その幕の**末尾へ**移動。並びを保ちたいなら `index` を必ず添える |
| どちらも渡さない | 位置は動かない |

新規作成では `section_id` が要る。ただし幕が 1 つしか無い作品では省略できる。
2 つ以上あるのに省略すると `section_id が必要です` で弾かれる。

**`index` は書き込みのたびに振り直される。** 1 回の `get_plot` を見ながら
「3 番目に 1 枚、6 番目に 1 枚」と続けて挿入すると、2 枚目は狙いより 1 つ後ろに入る。
新規作成も移動も、範囲外の `index` は端へ丸められるので、ずれても書き込みは成功する。

対処は 2 つのどちらか。後ろから前へ処理する（幕の末尾側の挿入・削除を先に済ませる）か、
1 回書くごとに手元の並びを更新してから次の `index` を決める。
複数枚を触ったら、最後に `get_plot` の幕内の連番を見て、意図した位置にあるかを 1 枚ずつ確かめる。

### 6.5 `status` は英語の 4 値だけ

`idea` / `fixed` / `writing` / `done`。`get_plot` の表示は `検討中` / `確定` / `執筆中` / `済` だが、
表示のラベルをそのまま渡すとエラーになる。

### 6.6 実在チェックがある項目・ない項目

| 項目 | チェック |
|---|---|
| `line_ids` | あり。存在しない `line_id` はエラー |
| 伏線の `plant_beat_id` / `payoff_beat_id` | あり |
| 秘密の `reveal_beat_id` | あり |
| `pov` / `cast` / `place` / `episode_id` | **なし。** 誤った id も通り、表示から名前が消えるだけ |

### 6.7 要約・メモに書く日本語

`summary` / `note` の作法と記法は `kotonaha-mcp.md` §7 に従う。

プロットは公開されないので、要約とメモには真相をそのまま書いてよい。
危ないのは、その文を用語集へ持っていくとき（§7.4）。

## 7. 書き込んだあとの検算

`get_plot` を読み直す。読み直さずに終わらない。

### 7.1 数を比べる

§1 で控えた行と並べる。

```
改修前 → 改修後
- 未回収 4 → 4（増えていない）
- 根なし 0 → 0
- 未配置 1 → 1
- 開示未定 2 → 1（「ユキの正体」に reveal を置いたぶん減）
- 「（削除済みビート）」 0 件 → 0 件
```

`[未回収]` `[根なし]` `[未配置]` `[開示未定]` の**どれかが増えていたら、原因を特定して直す**。
直せない（作者の判断待ちなど）なら、なぜ残るのかを言葉で説明して残す。理由なしで残さない。

### 7.2 文字列で探す

- `（削除済みビート）` … 1 件でもあれば張り替え漏れ。張り直す先が決まっているなら、
  `upsert_foreshadow` / `upsert_secret` に新しいビートの id を渡す。決まっていないなら
  空文字を渡して参照を外す（`plant_beat_id: ""` / `payoff_beat_id: ""` / `reveal_beat_id: ""`）。
  外すと表示が `未定` に戻り、この文字列は消える。放置すると、作者の画面にこの先ずっと出続ける
- 触ったビートの `視点:` `登場:` `舞台:` … 名前が改修前と同じ顔ぶれで出ているか
- 触った幕の見出し … `（Nビート・予定 M字）` が想定どおりか
- 幕内の連番 … 新しいビートが意図した位置に入っているか

### 7.3 中身を確かめる

- **元の指摘（着手前に 1 行で書いたもの）が消えているか。** 指摘の文をそのまま読み返して、
  いまのビート列でその指摘がもう成り立たないことを確かめる。ここを飛ばすと、
  「作業はしたが指摘は残っている」で終わる
- **当てた角度をもう一度当てる。** `structure-angles.md` §1 で「そして」を数えたなら数え直す。
  減っていないなら、動かしただけで直っていない
- **世界観設定に反していないか。** `get_plot` の冒頭に世界観設定が丸ごと載っているので、
  読み直すのに追加の呼び出しは要らない。ビートの改修で踏み抜きやすいのは、
  `rules`（この作品の約束事）、`forbidden`（やらないこと）、`reveal`（何をいつ明かすか）、
  `style`（語り手と文体）、`structure`（話の組み立て）の 5 枠。
  視点・人称の決め事（`style`）と、1 話の長さ・引きの決め事（`structure`）を落としやすい
- **伏線の順序。** 張るビートが回収ビートより物語順で前にあるか（検査されない）
- **孤児の話が出ていないか。** ビートを消す前に、その行の `対応話: 第七話 [episode_id: ep-07]` を
  そのまま控える。消したあと `get_plot` の中でその `episode_id` を探し、どのビートにも出てこなければ、
  その話は孤児。`get_work` は読まない。話ごとに取り出す手段が無く、作品の本文が全話まとめて返るだけで、
  しかも `get_work` の出力に `episode_id` は付かない。話数と `対応話` の数はもともと一致しない
  （ビートに紐付けていない話は普通にある）ので、突き合わせても何も分からない
- **`作中時間` の連なり。** 並べ替えた区間を頭から読み、相対表現がずれていないか

### 7.4 終わりの報告と申し送り

4 点だけ。長く書かない。

1. 直したこと（元の指摘がどう解消したか）
2. 書き込んだもの（どのビート・伏線・秘密を、どう変えたか。新しい id も）
3. 残したもの（判断待ち・別件として切り出した壊れ）
4. 次にやること（本文の改稿があるなら、どの話のどこを直すのかまで書いて `novel-writing` へ）

用語集へ足す必要が出たら `glossary-deepdive` へ渡す。渡すときに、その文が
**`summary`（読者に見える）へ行くのか `author_note`（公開時に落ちる）へ行くのか**まで書いて渡す。
ビートの要約に書いた真相をそのまま持っていくと、公開される欄に落ちる。

アプリで「AIの変更を取り込む」を押すまで手元に反映されないことを、最後に 1 行添える。
