# 波及範囲の洗い出しと、書き込みの順番

ビートは単独のカードではない。伏線・秘密・プロットライン・用語集・本文・幕の並びが、
そのビートの id と位置に乗っている。**1 枚動かすと、警告を出さずに壊れるものがある。**
この文書は「何が壊れるか」と「壊さない順番」を、`get_plot` の出力の見方まで落として書く。

---

## 1. 着手前に、いまの状態を数えて控える

検算（§7）は「増えていないか」で行う。**基準が無いと増えたことに気づけない。**
`get_plot` を読んだ時点で、次を数えて会話の中に書き出しておく。

```
改修前の状態（2026-08-28 時点）
- 伏線 12 件：回収済 7 ／ 未回収 4 ／ 根なし 0 ／ 未配置 1
- 秘密 5 件：開示予定 3 ／ 開示未定 2 ／ 明かさない 0
- 幕 4 ／ ビート 23 ／ 対応話つきのビート 9
- 「（削除済みビート）」の出現 0 件
```

`（削除済みビート）` は、伏線・秘密が指しているビートが消えているときに出る文字列。
**改修前が 0 件でないなら、それは今回の改修より前からある壊れ**なので、混ぜずに別件として作者へ報告する。

`※ 他に N 件のプロット案があります` の行が出ていたら、そこで止めて作者に伝える。
MCP が触るのは主プロット 1 本だけで、残りは読むことも書くこともできない。
作者が別案のほうを直したいつもりなら、この改修は最初から相手が違う。

---

## 2. 対象ビートを特定する — 伏線・秘密の行に beat_id は出ない

ここが最初の落とし穴。ビートの行には id が出る。

```
3. [確定] 港で待つ [beat_id: b-7a2]
   要約: ユキは桟橋で三時間、船を見送る
   視点: ユキ ／ 登場: ユキ、母 ／ 舞台: 桟橋 ／ 作中時間: 三日後の夕方
   ライン: ユキの決断 ／ 予定: 3,000字 ／ 対応話: 第七話 [episode_id: ep-07]
```

ところが伏線と秘密の行は、参照先を **id ではなくビートのタイトルへ解決して**表示する。

```
伏線:
- [未回収] 錆びた鍵 [foreshadow_id: fs-1]（張る: 港で待つ → 回収: 未定）
秘密（読者に伏せる情報）:
- [開示未定] ユキの正体 [secret_id: sc-1]（読者に明かす: 未定）
```

つまり **`b-7a2` で全文検索しても、この伏線は引っかからない**。
辿るには、対象ビートの**タイトル文字列**（ここでは「港で待つ」）で `get_plot` 全文を検索する。

同じタイトルのビートが 2 枚あると、この方法では区別がつかない。
その場合は先にどちらかを改題する（`upsert_plot_beat` に `id` と `title` だけ渡す。
改題はビートのタイトルを変えるだけで、本文にも伏線の紐付けにも影響しない）。

## 3. 触るビートごとに、7 つのつながりを拾う

対象ビート 1 枚につき、次を全部埋める。埋まらない欄があるまま書き込みへ進まない。

### 3.1 伏線（`plant_beat_id` / `payoff_beat_id`）

タイトル検索で、そのビートが `張る:` か `回収:` に出ている伏線を全部拾い、`foreshadow_id` を控える。

| そのビートをどうすると | 伏線はどうなる |
|---|---|
| 削除する（張る側だった） | 回収側が残っていれば `[根なし]`、両方消えれば `[未配置]` |
| 削除する（回収側だった） | `[未回収]` に戻る |
| 別の幕へ動かす | 状態は変わらないが、**張る→回収の順序が逆転していないか**は自動では検査されない |

順序逆転は導出ロジックが見ていない。物語順（幕の並び → 幕内の並び）で、
張るビートが回収ビートより後ろに来ていないかは**自分で目視する**。

### 3.2 秘密（`reveal_beat_id`）

同じくタイトル検索で `読者に明かす:` に出ている秘密を拾う。

削除すると `[開示未定]` に落ちる。ここに追加の罠がある。
**`reveal_beat_id` を設定した時点で、その秘密の「明かさない」印は消える**
（明かすビートが決まっている秘密に「最後まで伏せる」印を残さない設計）。
だから「明かさない」だった秘密に一度 `reveal_beat_id` を付け、あとでそのビートを消すと、
`[明かさない]` には戻らず `[開示未定]` になる。元へ戻すには `keep_hidden: true` を渡し直す。

### 3.3 プロットライン（`line_ids`）

ビート行の `ライン: ユキの決断` は**名前だけ**で、`line_id` は出ない。
id は `get_plot` の冒頭にまとまっている。

```
プロットライン: 本筋 [line_id: ln-1]、ユキの決断 [line_id: ln-2]、母の側 [line_id: ln-3]
```

配列を組み直すときは、ここで名前 → `line_id` を引く。
ラインを丸ごと消すと（`delete_plot_item` の `kind: line`）、全ビートの `line_ids` から自動で外れる。
これは唯一「参照を黙って掃除する」削除なので、ラインの削除は影響が広い。

### 3.4 視点・登場・舞台（用語集の `entry_id`）

ここも `get_plot` には**名前しか出ない**。`entry_id` は `get_glossary` の `[entry_id: …]` で引く。

見えない壊れ方が 2 つある。

- **存在しない `entry_id` を渡してもエラーにならない。** `line_ids` だけは実在チェックがあるが、
  `pov` / `cast` / `place` / `episode_id` は素通りする。id を打ち間違えると、
  書き込みは成功したのに `get_plot` の `登場:` からその名前が消える。「消えた」ようにしか見えない。
- **用語集の項目を削除すると、参照していたビートの欄から名前が黙って減る。** 警告は出ない。
  改修前後で `登場:` の人数が変わっていないかを見る。

### 3.5 対応話（`episode_id`）と `status`

`対応話: 第七話 [episode_id: ep-07]` が出ていたら、**そのビートには本文がある**（§4）。

`status` は `検討中` / `確定` / `執筆中` / `済` の 4 つ。
`執筆中` と `済` は、`episode_id` が付いていなくても「もう書いた」の申告として扱う。

### 3.6 作中時間（`time_label`）

`三日後の夕方` のような相対表現は、**直前のビートを基準にしている**ことが多い。
ビートを並べ替えると、文字列はそのままで意味だけがずれる。
並べ替えの対象になった区間の `作中時間` は、順に読み直して辻褄を確かめる。

### 3.7 幕内の位置（`index`）と予定文字数

`get_plot` はビートを **1 始まり**で番号付けして表示するが、`upsert_plot_beat` の `index` は
**0 始まり**。表示上「3.」のビートの `index` は `2`。ここを 1 つずらす事故が最も多い。

幕の見出しには小計が出る。

```
## 第二幕・前 [section_id: s-2]（5ビート・予定 14,000字）
```

ビートを幕をまたいで動かすと、この小計が両方の幕で変わる。
連載のペース配分を作者が数字で持っているなら、動かす前後の小計を並べて見せる。

## 4. 本文が書かれているビートは、本文の改稿とセットでしか動かせない

### 4.1 線引き

| ビートの状態 | 動かしてよいか |
|---|---|
| `検討中` / `確定` で `対応話` なし | 自由。要約・順番・削除まで作者の合意だけで足りる |
| `執筆中` / `済`、または `対応話` あり | **本文の改稿とセット。** 単独では動かさない |

`対応話` の有無が最も硬い信号。`status` は付け替え忘れが起きるが、`episode_id` は
作者が明示的に紐付けたものなので、付いているなら本文が存在する。

### 4.2 何をすると本文が壊れるか

- **要約・メモの書き換え**（`summary` / `note`）… 本文と食い違うだけで、本文は壊れない。
  ただし食い違ったままにすると、次に本文を書く人（作者でも AI でも）が要約を信じて誤る。
  ずれるなら、そのずれを `note` に 1 行残す。
- **`index` / `section_id` の変更**（並べ替え・幕移動）… **読者が読む順が変わる。**
  該当話とその前後の話で、既出・未出の情報が入れ替わる。改稿必須。
- **`pov` の変更**… 本文の人称・視点そのものの変更。全面改稿。
- **削除**… `delete_plot_beat` で消えるのはビートのカードだけで、**本文の話は消えない**。
  話は残り、どのビートからも参照されない「孤児の話」になる。データは失われないが、
  プロットと本文の対応が切れるので、話をどうするか（残す・統合する・作者が消す）を必ず決める。

### 4.3 作者への確認の文面

黙って動かさない。次の形で、対象・影響・選択肢まで出して聞く。

> 動かしたいビートのうち 2 枚に本文があります。
>
> - 「港で待つ」[確定]／対応話: 第七話（4,200字・執筆済み）
> - 「母の電話」[済]／対応話: 第八話（3,800字・執筆済み）
>
> この 2 枚の順番を入れ替えると、読者が「母が島を出た」と知る位置が 1 話ぶん早まります。
> 第七話の冒頭 3 段落（母がまだ島にいる前提の描写）と、第八話の引き（電話が鳴って終わる）が、
> どちらもそのままでは通りません。
>
> 選べるのは 3 つです。
> (A) 順番は変えず、第七話の中で母の不在を先に匂わせる（本文の直しは 3 段落だけ）
> (B) 順番を入れ替え、第七話・第八話とも冒頭と引きを書き直す（各 1 時間程度）
> (C) いま決めず、プロット側だけ案として作り、本文は次の推敲でまとめて直す
>
> 私は (A) を推します。入れ替えで得られるのは「母の不在を先に知る」1 点だけで、
> それは第七話の中の 3 段落でも同じ効果が出ます。書いた 8,000 字を触る理由としては軽い。
>
> どれにしますか。決まるまでプロットには書き込みません。

## 5. 直し方の案を 3 つ出す型

粒度を変えて 3 つ並べる。**それぞれに「何が良くなるか」と「何を失うか」を必ず書く。**
失うものは、時間・文字数・書いた本文・世界観設定の決め事のどれかで、具体で書く。
最後に編集者としてどれを推すかと、その理由を言う。決めるのは作者。

### 5.1 3 つの粒度

| 案 | 触る範囲 | 本文への影響 |
|---|---|---|
| 最小 | 既存ビートの `summary` / `note` / `time_label` だけ | なし |
| 中 | ビートを 1〜2 枚足す・並べ替える。伏線を 1 本新設する | 新しい話が増える／前後の引きを直す |
| 根本 | 幕の構成、視点の担い手、賭け金の持ち主を変える | 執筆済みの話の全面改稿。世界観設定の決め直しを伴うことがある |

### 5.2 提示の文面（例）

指摘：`glossary-deepdive` で「ユキが怖いのは船ではなく、出ていく側になること」と決まった。
第二幕のビート「港で待つ」は、ユキが誰かの出発を見送るだけで、ユキ自身の選択が入っていない。
第三幕「島を出る」への布石も無い。

> **A. 最小 — 「港で待つ」の中身だけ書き換える**
> 要約を「三時間、船を見送る」から「三時間、乗らない理由を数えている」に変え、
> `note` に「送る側にしか立てないユキ」を残す。触るのはビート 1 枚。
> - 良くなる：用語集との食い違いが消える。作業は 10 分。本文（第七話）とも矛盾しない
> - 失う：第二幕でユキが動かない問題はそのまま。第三幕「島を出る」は依然として唐突
>
> **B. 中 — 「切符を買って捨てる」を 1 枚足す**
> 「港で待つ」の直後（第二幕・前の 4 番目）に新設。ユキが一度は出ていく側に回ろうとして、
> 桟橋で切符を捨てる。伏線「捨てた切符」を新設し、張る＝このビート、回収＝第三幕「島を出る」。
> - 良くなる：第二幕にユキ自身の選択が 1 つ入る。第三幕の決断に助走がつく。
>   未回収の伏線が 1 本増えるが、同じ改修の中で回収まで置くので `[回収済]` で着地する
> - 失う：第二幕が 1 話（3,000 字）伸びる。第七話と第八話の間に 1 話増えるので、
>   連載の話数が 1 つずれる。第八話の冒頭が「翌朝」始まりなので、そこも 2 行直す
>
> **C. 根本 — 第二幕の視点を母へ移す**
> 「港で待つ」を母の視点で書き直し、ユキが動けないのは母が縛っているからだと読者に見せる。
> - 良くなる：第二幕の停滞が「停滞そのものがドラマ」に変わる。母のラインが本筋に合流する
> - 失う：第七話（4,200 字）・第八話（3,800 字）の全面改稿。
>   さらに世界観設定の `style` に「一人称・ユキ視点で固定」とあるので、**この決め事の変更が先**になる。
>   世界観設定を変えると、既存の全話がその決め事の対象になる
>
> **推し：B。** A では用語集との食い違いが消えるだけで、第二幕でユキが動かないという
> もとの弱さが残ります。C は効きますが、代償が `style` の決め直しまで届くので、
> いま払う額としては大きすぎる。B は 3,000 字の追加で、第三幕の決断の説得力まで届きます。
>
> どれにしますか。別の案があればそちらを聞きます。

**作者が第 4 の案を出したら、それがより良ければ採る。** 採る理由まで言葉にする。

## 6. 書き込む — 順番を守る

### 6.1 順番

```
0. create_backup（まとまった書き換えの前。cloud 会員のみ。失敗したら作者へ伝えて可否を聞く）
1. 幕が足りなければ upsert_plot_section で先に作る（beat の section_id に要るため）
2. 新しいビートを upsert_plot_beat（id を渡さない）で作り、返ってきた beat_id を控える
3. 位置を決める（section_id と index）
4. 伏線 upsert_foreshadow の plant_beat_id / payoff_beat_id を新しい beat_id へ張り替える
5. 秘密 upsert_secret の reveal_beat_id を張り替える
6. 最後に、不要になったビートを delete_plot_beat で消す
```

### 6.2 なぜこの順番なのか

`upsert_foreshadow` の `plant_beat_id` / `payoff_beat_id` と `upsert_secret` の `reveal_beat_id` には
**実在チェックがある**。存在しないビート id を渡すと `… のビートが見つかりません` で弾かれる。
だから張り替え先のビートが先に無いといけない。

逆に、古いビートを先に消すと 2 つのことが起きる。伏線が `[根なし]`、秘密が `[開示未定]` に落ち、
その状態がライブスナップショットに保存される。この間に作者がアプリを開くと、
壊れた途中経過を見ることになる。**壊れた状態を一度も保存しない順番が、この順番。**

### 6.3 幕を削除するときの挙動

`delete_plot_item` の `kind: section` は、幕の中のビートを**隣の幕の末尾へ移す**。
隣は前の幕が優先で、先頭の幕を消したときだけ次の幕になる。ビートは消えない。

ただし移った先では**末尾に付く**。元の並び順は保たれるが、位置は幕の最後になる。
幕を消したら、移動したビート群の `index` を必ず組み直す。

**最後の 1 幕は削除できない**（`最後の幕は削除できません（ビートの行き場が無くなるため）`）。
幕を減らして 1 つにしたいなら、先に全ビートを残す幕へ移してから、空になった幕を消す。

幕の並べ替えは `upsert_plot_section` に `id` と `index` を渡す。

### 6.4 書き込みはアプリへ即時には映らない

MCP の書き込みが入るのはライブスナップショット側で、
作者のアプリには「AI の変更を取り込む」を押すまで反映されない。

だから、**書き込む前に「いまアプリでプロットを編集していないか」を聞く**。
両側で同じプロットを触ると、取り込みのときにどちらかが負ける。
書き終えたら、取り込みが要ることを 1 行添える。

## 7. パッチ方式の落とし穴

`upsert_plot_beat` は **渡した項目だけ書き換える**。省略＝据え置き、空文字＝未設定に戻す。
ここまでは `upsert_glossary_entry` と同じ。**違うのは配列**。

### 7.1 配列は丸ごと置換される

`cast` / `place` / `line_ids` は、渡すと**その内容で置き換わる**。追記ではない。

```jsonc
// 悪い例：登場人物に「船頭」を 1 人足すつもり
{ "work_id": "w1", "id": "b-7a2", "cast": ["gl-boatman"] }
// → 結果：登場が「船頭」だけになる。ユキと母が消える
```

```jsonc
// 正しい：現在の全員を entry_id で並べ、そこへ 1 人足す
{ "work_id": "w1", "id": "b-7a2", "cast": ["gl-yuki", "gl-mother", "gl-boatman"] }
```

現在の全員は `get_plot` の `登場: ユキ、母` から**名前で読み、`get_glossary` で entry_id に引き直す**。
`get_plot` には entry_id が出ないので、この往復を省けない。

このとき、用語集から消えた項目を指す参照は `get_plot` に名前が出ていないので、
組み直した配列からは落ちる。掃除にはなるが、**気づかないうちに何かを落としている**可能性があるので、
改修前後で登場人数が合っているかを見る。

### 7.2 触らない項目は渡さない

要約だけ直すなら、渡すのは 3 つだけ。

```jsonc
{ "work_id": "w1", "id": "b-7a2", "summary": "三時間、乗らない理由を数えている" }
```

「ついでに現在値を全部渡して揃える」をやると、写し間違えた 1 箇所が黙って消える。
**据え置きたいものは書かない**のが最も安全。

### 7.3 空文字と 0 の効き方

| 渡すもの | 起きること |
|---|---|
| `summary: ""` | 要約が消える。`guide` があればガイド文の表示に戻る |
| `note: ""` | メモが消える |
| `pov: ""` | 視点が未設定に戻る |
| `time_label: ""` | 作中時間が未設定に戻る |
| `episode_id: ""` | 本文との紐付けだけが切れる（**話そのものは消えない**） |
| `target_length: 0` | 予定文字数が未設定に戻る。幕の小計からも抜ける |
| `title: ""` | **何も起きない。** 空のタイトルは無視され、元のタイトルが残る（タイトルは消せない） |
| `cast: []` | 登場が空になる（`[]` は「空の配列で置換」であって、省略とは違う） |

### 7.4 `section_id` と `index` の組み合わせ

| 渡し方 | 起きること |
|---|---|
| `index` だけ | **いまの幕の中で**その位置へ並べ替え |
| `section_id` と `index` | その幕のその位置へ移動 |
| `section_id` だけ | その幕の**末尾へ**移動。並びを保ちたいなら `index` を必ず添える |
| どちらも渡さない | 位置は動かない |

新規作成では `section_id` が要る。ただし**幕が 1 つしか無い作品では省略できる**。
2 つ以上あるのに省略すると `section_id が必要です` で弾かれる。

### 7.5 `status` は英語の 4 値だけ

`idea` / `fixed` / `writing` / `done`。`get_plot` の表示は `検討中` / `確定` / `執筆中` / `済` だが、
**表示のラベルをそのまま渡すとエラー**になる。

### 7.6 実在チェックがある項目・ない項目

| 項目 | チェック |
|---|---|
| `line_ids` | あり。存在しない line_id はエラー |
| 伏線の `plant_beat_id` / `payoff_beat_id` | あり |
| 秘密の `reveal_beat_id` | あり |
| `pov` / `cast` / `place` / `episode_id` | **なし。** 誤った id も通り、表示から名前が消えるだけ |

### 7.7 要約・メモに書く日本語

`summary` / `note` は `natural-japanese` の作法で書く。前置きを書かない、結論から、一文一義。
記法は本文と共通で `[[用語]]`／`｜漢字《かんじ》`／`《《強調》》` が効く。
`[[ ]]` は用語集に無い語でも書けてしまうが未解決のまま残るので、**既存の項目名に合わせる**か、
先に用語集へ項目を作る（作るなら `glossary-deepdive` へ渡す）。

## 8. 書き込んだあとの検算

`get_plot` を読み直す。読み直さずに終わらない。

### 8.1 数を比べる

§1 で控えた数と並べる。

```
改修前 → 改修後
- 未回収 4 → 4（増えていない）
- 根なし 0 → 0
- 未配置 1 → 1
- 開示未定 2 → 1（「ユキの正体」に reveal を置いたぶん減）
- 「（削除済みビート）」 0 件 → 0 件
```

`[未回収]` `[根なし]` `[未配置]` `[開示未定]` の**どれかが増えていたら、原因を特定して直す**。
直せない（作者の判断待ちなど）なら、なぜ残るのかを言葉で説明して残す。黙って残さない。

### 8.2 文字列で探す

- `（削除済みビート）` … 1 件でもあれば張り替え漏れ。伏線・秘密のどちらが残っているかを見る
- 触ったビートの `視点:` `登場:` `舞台:` … 名前が改修前と同じ顔ぶれで出ているか
- 触った幕の見出し … `（Nビート・予定 M字）` が想定どおりか
- 幕内の連番 … 新しいビートが意図した位置（何番目）に入っているか

### 8.3 中身を確かめる

- **元の指摘（着手前に 1 行で書いたもの）が消えているか。** 指摘の文をそのまま読み返して、
  いまのビート列でその指摘がもう成り立たないことを確かめる。ここを飛ばすと、
  「作業はしたが指摘は残っている」で終わる
- **世界観設定に反していないか。** `get_plot` の冒頭に世界観設定が丸ごと載っているので、
  読み直すのに追加の呼び出しは要らない。とくに `rules`（この作品の約束事）、
  `forbidden`（やらないこと）、`reveal`（何を、いつ明かすか）の 3 枠を、
  今回足したビートの要約と突き合わせる
- **伏線の順序。** 張るビートが回収ビートより物語順で前にあるか（自動では検査されない）
- **孤児の話が出ていないか。** ビートを消したなら、その `episode_id` の話が
  どのビートからも参照されない状態になっている。`get_work` の話数と、
  `get_plot` に出る `対応話` の数を突き合わせる
- **`作中時間` の連なり。** 並べ替えた区間を頭から読み、相対表現がずれていないか

### 8.4 終わりの報告

4 点だけ。長く書かない。

1. 直したこと（元の指摘がどう解消したか）
2. 書き込んだもの（どのビート・伏線・秘密を、どう変えたか。新しい id も）
3. 残したもの（判断待ち・別件として切り出した壊れ）
4. 次にやること（本文の改稿があるなら、どの話のどこを直すのかまで書いて `novel-writing` へ）

アプリで「AI の変更を取り込む」を押すまで手元に反映されないことを、最後に 1 行添える。
