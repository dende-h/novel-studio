# toc-copy — LP・アプリ内文言

コトノハ-leaf- がユーザーに見せる文章を、プロダクトのトーンに揃えて書くためのスキル。
工程は「トーンと用語の確認 → 執筆 → 機械検査（textlint） → 文脈レビュー」。

## 1. 書く前に

`references/tone-and-terms.md` を読む。トーンの軸は——静かで誠実、誇張しない、不安で煽らない、
ユーザーの「書く」を主語にする。用語は既存 UI と揃える（同ファイルの用語表）。

UI 部品の文言（ボタン・ダイアログ・トースト・エラー・空状態）は `references/microcopy-patterns.md`
の型に従う。書く場所の当たりは `docs/CODEMAP.md`（LP は `public/lp/index.html`、画面は
`src/ui/components/`）。

## 2. 執筆の原則

- 事実で語る。機能名・数字・動作を名指しし、「様々な」「充実の」で束ねない
- ユーザーがすることを動詞で言い切る（「開けば、書き始められます」）。勧誘定型（〜してみませんか）に逃げない
- 不安を煽って課金・登録に誘導しない。リスク（端末の故障等）は事実として静かに伝え、対策を選択肢として示す
- 原稿の扱い（ローカル保存・何がサーバに送られるか）に触れる文言は、正確さを最優先にする。
  誇張も省略もしない（信頼がプロダクトの核）
- 文は敬体。見出しは体言止め・言い切りも可。読点でリズムを作る LP の文体（「原稿は、あなたの手元に。」）は
  LP と大きな見出しに限り、UI の実務文言では簡潔さを優先する

## 3. 機械検査

まとまった量の文言（LP のセクション、ヘルプ、お知らせ等）はドラフトをスクラッチパッドの一時ファイルに
書き出して検査する。ボタンラベル1個のような短文はかけなくてよい。

```bash
pnpm --dir tools/novel-textlint install       # 初回のみ
pnpm --dir tools/novel-textlint lint:copy <ファイル>
```

`【要修正】`（誇張マーケ語・AI 常套句）は原則直す。`【要検討】` は文脈で判断する。
誤検知が続く語はユーザーに確認のうえ `tools/novel-textlint/dict/ai-cliche-copy.json` を調整する。

## 4. レビュー

- その文言が出る瞬間のユーザーの状態（初見か、エラー直後か、課金判断中か）を想像して読み直す
- 既存画面の語彙・敬体と揃っているか。同じ概念に別の語を使っていないか
- 削れる語を削る。UI 文言は1文が短いほど強い
- 実装に反映する場合は該当コンポーネントの周辺文言も見て、浮いていないか確認する
