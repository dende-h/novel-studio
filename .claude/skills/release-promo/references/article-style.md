# note 記事の書き方（本人の手直しから抽出）

本人が初稿を手直しして公開した記事から拾った規則。初稿を書く前に読み、書いたあとにもう一度突き合わせる。

公開済みの手本（新しい順）

- 2026-10-02「脚本を原稿用紙の体裁で書いて Word に書き出す機能」 https://note.com/shiny_sheep9674/n/n1a0c8a8d0146
- 2026-09-27「小説をサウンドノベル形式で出力する機能」 https://note.com/shiny_sheep9674/n/nfaa91a7be611
- 2026-08-19「小説を書くためのエディタと、投稿サイトを作りました」 https://note.com/shiny_sheep9674/n/nba288e20c0dd

書く前に、いちばん新しい手本の本文を取って読む（WebFetch は要約しか返さないので、公開 API を使う）。

```bash
curl -sL -A "Mozilla/5.0" "https://note.com/api/v3/notes/<記事キー（URL の n から始まる部分）>" -o note.json
```

`data.body` が本文の HTML。見出し（h2/h3）・段落・箇条書き・画像のキャプション・末尾のリンクの形を確かめる。

## 形

- **タイトル**：いちばん目を引く機能ひとつを「〜する機能」の名詞句で（例「書き上げた小説を推敲する機能」）。まとめ型（「この3週間で足したもの」）は使わない。
- **冒頭**：次の型で始める。前置きやつなぎ文（「順に紹介します」）は書かない。
  - 「前回の記事から◯週間ほどですが、**コトノハ-leaf-** に機能を足したので紹介します。」
  - 「今回のメインは**◯◯**です。」
  - 箇条書きで今回の更新を並べる（各項目の核を太字。項目は句点なし）
  - ヒーロー画像とキャプション
- **見出し**：H2 は機能ごと。メインの機能だけ H2 の下に H3 を立てる。小さい機能は H2 ひとつに本文1〜2段落とスクショ（「〜を追加」「〜を載せました」のような平叙）。leaf と grove の両方を更新したときだけ、H2 を製品ごとにしてよい。
- **箇条書き**：句点なしのリード行（「確認できるもの」）の直後に置く。選択肢の列挙も箇条書きに開く。ただし似た項目は1行にまとめてよい（「字下げ、閉じ括弧の前の句読点、！？の後の空白」）。
- **画像**：本文の流れの直後に置き、キャプションは体言止めでよい。原稿では次の形で書く（本人が note に貼るときの目印）。

```
[画像: leaf-proofread.png]
（キャプション: 推敲の画面。左が本文、右が気になる箇所の一覧）
```

- **分量**：本文 1,800〜2,500 字、画像 10〜13 枚。機能によっては見出しとスクショだけでよい。
- **末尾**：「最後に」→「最後まで読んでいただき、ありがとうございました。」→ 2製品のリンク（URL を必ず付ける）。

```
- [コトノハ-leaf- — 登録なしで、すぐに書き始められます](https://cotonoha-leaf.org/)
- [コトノハ-grove- — 第1話はログインなしで読めます](https://grove.cotonoha-leaf.org/)
```

## 書かないこと

- **口語的なくだけた言い方**：「書くほう」「読むほう」のような言い方は使わない（2026-10-23 の指摘）。製品名はコトノハ-leaf-／コトノハ-grove- と書く。
- **引用ブロック（>）**：強調は太字の一文で。
- **設計理由・経緯**：「〜だからこう作った」「旧仕様をやめた理由」は落とす（例外は本人が「最後に」で自分で書くとき）。
- **課金・プランの線、制限の数字**：「無料20／有料50」のような上限は書かず「自分で用意したものも追加できます」と丸める。量を誇れる数字（素材数など）は残してよい。使える条件は1文で事実だけ（「推敲の画面はパソコンで使え、無料のアカウント登録が必要です」）。
- **決め台詞・警句**：「地味ですが、効きます。」「ここがいちばん大事なところです。」
- **記事内の相互参照**：「（後述）」。
- **次の予定**。

## 文体

- です・ます。関係のある2文は「〜ので、」「〜し、」でつなぎ、短文を畳みかけない。
- 太字は製品名、冒頭の箇条書きの核、各節の要点の一文（1節に1〜2か所）。
- 機能の動詞は素直に（「追加しました」「〜できるようにしました」「〜に対応しています」）。
- 本人がよく使う言い回し：「本文を勝手に書き換えることはありません」「〜は前回書いたとおりです」。
- 体言止めはごくたまに。

## 「最後に」

本人が自分の経験（例：シナリオセンターで脚本を学んでいた話）で書き直す節。Claude は経緯や体験を作らない。初稿は次の範囲で控えめに書き、報告で「ご自身の言葉に直してください」と伝える。

- 機能が役に立つ場面を一般論で1〜2文（「表記ゆれや字下げの抜けを目で探すのは、思った以上に手間がかかります」）
- できることとできないことを正直に（「形の部分だけで、文章の良し悪しまでは判断しません」）
- 「まだ荒いところもあると思うので、気づいたことは掲示板で教えてください。」

## AI っぽさの点検（natural-japanese スキル・フル）

書き上げたら、**Skill ツールで natural-japanese を読み込み**、その手順の「フル」で回す（公開記事なので。目安 7〜10 分）。省略しない。

1. 画像の目印を除いた本文を作る（`[画像: …]` と `（キャプション: …）` の行が「文頭の反復」として拾われるため）。

   ```bash
   grep -v "^\[画像\|^（キャプション" note-article.md > <作業>/body.md
   ```

2. 機械の検査を回す。uv が入っていない環境では python3 で直接動かす（`-I` を付けると同じフォルダの `textcore.py` を読めないので付けない）。

   ```bash
   NJ=.claude/skills/natural-japanese/scripts
   python3 $NJ/lint.py --genre essay --json <作業>/body.md > <作業>/lint1.json   # AI 臭（禁止語・翻訳調・リズム）
   python3 $NJ/lint.py --reading-load <作業>/body.md                           # 読解負荷の指さし
   python3 $NJ/outline.py <作業>/body.md > <作業>/outline.txt                  # 見出しと段落の頭（構造レビュー用）
   python3 $NJ/terms.py <作業>/body.md                                         # 初出の用語
   ```

   手本の記事にも同じ lint をかけて、`low_burstiness`（文の長さの起伏）の値を比べる。本人の記事でも出る指摘なので、手本（2026-10-02 は -0.33）より大きく下回るときだけ、長い文を分けて詰める。

3. 構造レビューと読みやすさレビューを、サブエージェント2つに**並行で**頼む。ファイルの中身は貼らず、パスを渡す。
   - 構造：原稿・outline.txt・手本の本文・このファイル・natural-japanese の `references/writing-constitution.md` と `references/revision-guide.md`（同じ鋳型の反復・濃淡・重複）
   - 読みやすさ：原稿・手本の本文・このファイル・`references/readability-principles.md` と `references/readability-antipatterns.md`（A→J の順）・`references/forbidden-patterns.md`・`references/translationese.md`
   - どちらも「書き換えない・所見を重要度順に・行番号／引用／問題／直し案」で返してもらう。
4. 所見は一件ずつ「直す／残す（理由）」を決める。体験や経緯を作る直し案（「最後に」を一人称の体験にする等）は採らず、本人に任せる。
5. 直したら `--baseline <作業>/lint1.json` を付けて lint をかけ直し、新しい指摘が出ないことを確かめる。最後に初見の読者のつもりで通読し、同じ言い回しの重なりを拾う。
6. 中間ファイル（body.md・lint の JSON・outline.txt・手本の本文）は消す。
