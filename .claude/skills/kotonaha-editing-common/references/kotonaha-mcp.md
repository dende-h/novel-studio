# コトノハ-leaf- の器と、読み書きの手順

設定を詰めるスキルが共通で守る規約。**書き込みの事故はほぼ全部この文書のどこかに書いてある。**

## 1. サーバを選ぶ

本番が `-leaf-`、検証用が `stg`。既定は `-leaf-`（作者の実データ）。
作者が「stg で」「検証環境で」と言ったときだけ `stg` を使う。
ツール名はサーバ名込みで `mcp__-leaf-__get_world` の形になる。以下ではサーバ名を省いて書く。

## 2. 器は 4 つ。誰が読むかで分かれている

| 器 | 読む | 書く | 読者に見えるか |
|---|---|---|---|
| 本文 | `get_work` | `set_episode` / `add_episode` | 見える（公開すれば） |
| 用語集 | `get_glossary` | `upsert_glossary_entry` | **`name` と `summary` は見える** |
| 世界観設定 | `get_world` | `set_world_note` | 見えない |
| プロット | `get_plot` | `upsert_plot_beat` ほか | 見えない |

用語集は公開サイトへ送られ、**その用語が出てくる話まで読んだ読者に開く**。
段階公開なので「まだ先の話だから大丈夫」は通らない。その語が出る話を読者が読んだ瞬間に開く。

### 何をどこへ書くか

| 書きたいもの | 行き先 |
|---|---|
| 読者が引いて役に立つ説明（誰で、どこで、何なのか） | 用語集の `summary` |
| その項目 1 つに閉じた内緒（正体・後の展開・仕掛け） | 用語集の `author_note`（公開時に落ちる） |
| 作品全体のルール・世界の仕組み・執筆の決め事・開示方針 | `set_world_note` |
| 読者にいつ明かすか、という管理 | `upsert_secret` |
| 布石を張って回収する仕掛け | `upsert_foreshadow` |
| 出来事として起きること | `upsert_plot_beat` |

**迷ったら `author_note` か世界観設定へ置く。** 公開してよいと確信できるものだけが `summary` に載る。

### 公開事故になりやすい書き方

- 「実は◯◯の息子。第三幕で判明する」→ `summary` に書くと仕掛けが公開される。`author_note` へ。
- 「この作品では死者は生き返らない」→ 作品のルール。用語集ではなく `set_world_note`（`rules`）へ。
- 「読者にはユキの正体を最終話まで伏せる」→ 開示方針。`set_world_note`（`reveal`）と `upsert_secret` へ。
- 「連載は 1 話 3000 字、章末は必ず引きで閉じる」→ 執筆の決め事。`set_world_note`（`structure`）へ。
- 項目名を `【作者用】年表` のように付けている → 器を間違えた合図。世界観設定の自由枠へ移す。

## 3. 読む順番（例外なし）

1. `list_works` で `work_id` を得る。作品が複数あって指定が無ければ作者に聞く。
2. **`get_world`**。この作品の決め事。これを読まずに何も書かない。
3. `get_plot`。幕・ビート・プロットライン・伏線・秘密。冒頭に世界観設定が付いてくる。
4. `get_glossary`。既存の項目と `entry_id`。
5. 必要なら `get_work`。既に書かれた本文は動かせない前提として扱う。

順番に意味がある。世界観設定は作品ごとの前提で、そこに書かれたルールに反する提案は最初から出さない。

## 4. id の受け取り方

読み出しツールが返すテキストには id が埋め込んである。書き込みの対象はここから取る。

```
用語集      ## 名前 [entry_id: …]
              分類: 人物 ・ よみ: … ・ 別名: …
              （公開情報の本文）
              ### 作者メモ（非公開）
世界観設定  ## 時代と場所 [slot: stage, note_id: …]
幕          ## 第一幕 [section_id: …]
ビート      3. [確定] 港で別れる [beat_id: …]
              対応話: 第三話 [episode_id: …]
プロットライン  ユキの正体 [line_id: …]
伏線        - [未回収] 錆びた鍵 [foreshadow_id: …]（張る: … → 回収: 未定）
秘密        - [開示未定] ユキの正体 [secret_id: …]（読者に明かす: 未定）
```

状態の印は、そのまま点検の材料になる。

- ビート … `検討中` / `確定` / `執筆中` / `済`
- 伏線 … `未回収` / `回収済` / `根なし`（参照先のビートが消えた） / `未配置`
- 秘密 … `開示予定` / `開示未定`（明かす場所が決まっていない） / `明かさない`

## 5. 書き込みの規則

### 5.1 パッチのものと、全置換のもの

**`set_world_note` は `body` を全置換する。** ここが最も事故る。
追記のつもりで新しい一段落だけ渡すと、その枠に既にあった記述が消える。
必ず `get_world` で現在の本文を読み、**既存＋追加を組み立てた全文**を渡す。

`upsert_glossary_entry` / `upsert_plot_beat` / `upsert_secret` / `upsert_foreshadow` はパッチ方式。
渡した項目だけ書き換わり、省略した項目は据え置き、空文字を渡すとその項目が消える。
読みだけ直したいなら `reading` だけ渡す。`summary` を添えて渡し直す必要はない。

ただし **配列は渡すと丸ごと置換**される。`upsert_plot_beat` の `cast` / `place` / `line_ids`、
`upsert_glossary_entry` の `aliases` がこれにあたる。1 人足したいときも、
現在の全員＋1 人の配列を渡す。触らないなら渡さない。

### 5.2 消える操作

- `summary` に空文字 … 公開情報が消える
- `author_note` に空文字 … 作者メモが消える
- `set_world_note` の `body` に空文字 … その枠ごと削除される（定型枠は空を保存しない）
- `delete_glossary_entry` / `delete_plot_beat` / `delete_plot_item` / `delete_world_note`
  … 掘り下げの最中に呼ばない。削除は作者が明示的に決めたときだけ。

### 5.3 `name` は毎回必須で、変えると改名になる

`upsert_glossary_entry` は `work_id` と `name` が必須。**読みだけ直す更新でも `name` を渡す。**
そして渡した `name` が現在と違えば、それは改名として通る。既存の項目を更新するときは、
`get_glossary` が返した名前をそのまま渡す。表記を思い出しで書くと、意図しない改名になる。

改名そのものは安全に作られていて、旧名は自動で別名に残るので本文の `[[旧名]]` は解決され続ける。
危ないのは意図しない改名のほうで、別名が増えていき、いずれ他の項目と衝突してエラーになる。
`name` や別名が他の項目と完全一致する書き込みは拒否される。

### 5.4 分類（`category`）

画面の固定リストは **人物 / 場所 / 組織 / 用語 / アイテム / 生物** の 6 つ。
`upsert_glossary_entry` の説明文が「キャラ/用語/場所 等」と書いているせいで `キャラ` で作られやすいが、
固定リストの外の値は旧カテゴリ扱いになり、画面の分類から外れる。**`人物` と書く。**

### 5.5 廃止された欄

`upsert_glossary_entry` の `body` は旧フィールド。渡すと `summary` の末尾に結合される。
新しく書くときは `summary` に一本で書く。

### 5.6 順番を間違えると壊れるもの

ビートを差し替えるときは、**新しいビートを作って `beat_id` を得てから**、
伏線の `plant_beat_id` / `payoff_beat_id` と秘密の `reveal_beat_id` を張り替え、
最後に古いビートを消す。先に消すと、参照していた伏線が `[根なし]` になる。

幕を消すと中のビートは隣の幕へ移動する。最後の 1 幕は消せない。

## 6. 書き込む前と、書き込んだあと

**書き込む前に、作者の同意を取る。** 何を、どの器の、どの欄へ、どう書くのかを提示してから実行する。
掘り下げの途中で勝手に保存しない。

まとまった量を書き換えるときは `create_backup` で版を作っておく（cloud 会員の機能）。
失敗したら、その旨を作者に伝えて続けるかどうかを聞く。黙って進めない。

書いたあとは読み直す。用語集を書いたら `get_glossary`、プロットを触ったら `get_plot`。
`[未回収]` `[根なし]` `[開示未定]` が増えていないかを見る。

## 7. 器へ入れる日本語

用語集・世界観設定・プロットへ書く文は、**`natural-japanese` スキルの作法**で書く。
本文（話）だけが `novel-writing` の領分で、それ以外は仕事の文書として読みやすさを優先する。

短い欄でも最低限これは守る。

- 前置きを書かない。結論から。「本項目では」で始めない。
- 「〜と言えるでしょう」「重要なのは」「このように」「〜という側面もあります」を使わない。
- 因果は地の文でつなぐ。箇条書きは本当に並列なときだけ。
- 抽象語で埋めない。固有名詞・数・具体物を入れる。

数行を超えるものを書くとき、または仕上げの直前には `natural-japanese` を通す。

記法は本文と共通で、`[[用語]]`（用語集へのリンク）、`｜漢字《かんじ》`（ルビ・半角 `|` も通る）、
`《《強調》》`（傍点）が使える。効く欄はビートの要約・メモ、世界観設定の本文、
用語集の公開情報・作者メモ。`[[ ]]` は用語集に無い語でも書けるが、未解決のまま残るので、
先に用語集へ項目を作るか、既存の名前に合わせる。
